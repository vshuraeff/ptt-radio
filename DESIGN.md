# ptt-radio: дизайн голосовой рации

Голосовая рация для мультиплеера Factorio 2.1.23. Мод `ptt-radio` (Lua, ставится всем) задаёт каналы и права, передаёт сигнализацию через Lua UDP API и пересылает запасную игровую копию голоса. Компаньоны выбирают прямой UDP, серверный хаб или ретранслятор-игрок; без подходящего UDP-пути голос идёт через игру. Хаб необязателен. Игрок без компаньона и без флага `--enable-lua-udp` играет как обычно и видит подходящие по каналу плашки, но голоса не слышит. Карта компонентов и потоков — в [ARCHITECTURE.md](ARCHITECTURE.md).

Ниже разделены исторические замеры Lua UDP на одной машине (клиент macOS и headless-сервер Linux в VM), виртуальные аудиоустройства и модели сетевых путей. Замеры игрового пути включают доставку input actions и обработку по тикам. Их нельзя считать задержкой реальной сети или физических аудиоустройств; условия указаны у результатов.

## Свойства транспорта, на которых строится дизайн

Игровая копия пакета компаньона попадает в игру через `helpers.recv_udp()`, становится input action и через lockstep-мультиплеер приходит на все пиры как `on_udp_packet_received` с `player_index`, который проставляет движок. Этот раздел относится к игровому пути, а не к UDP между компаньонами:

- **В локальном прогоне порядок сохранялся.** На 15 000+ пакетах потерь и перестановок не было. Это наблюдение не гарантирует доставку при переполнении UDP-буфера, см. ограничения ниже. FEC по умолчанию выключен; приёмник всё же имеет упорядочивание, FEC/PLC и отсечение опоздавших кадров для потерь и нескольких путей.
- **Задержка может закончиться пачкой.** При автосохранении пакеты копились и приходили разом: RTT подскакивал со 116 мс до ~600 мс. На паузе `recv_udp` тоже не вызывается; буфер приёма ограничен. Приёмник сбрасывает лишний запас и маскирует пропуски.
- **Пакеты приходят пачками по тику**, с интервалом 16,7 или 33 мс. Глубина буфера 40–60 мс это покрывает.
- **Отправителя определяет движок.** Подделать «кто говорит» нельзя: мод берёт `event.player_index`, а не поле из пакета.
- **Весь голос получают все клиенты**, включая тех, у кого нет компаньона. Мод решает только, каким локальным компаньонам переслать пакет через `send_udp`. На сетевую стоимость он не влияет.
- **Экземпляр без флага не ломается.** `recv_udp` и `send_udp` там ничего не делают. Проверено в обе стороны.

## Мод `ptt-radio` (Lua)

### Состояние только по тикам

У мода нет часов, и он не должен их имитировать. Любые таймауты считаются через `game.tick`. Во время сохранения и паузы тики стоят, поэтому таймаут не сработает ложно на измеренной задержке в 600 мс.

- `storage.speakers[player_index] = last_tick`: выставляется после принятого `START3`/`VOICE3`, снимается на `STOP3`.
- `script.on_nth_tick(15)` снимает HUD говорящего, если `game.tick - last_tick > 30` (0,5 с игрового времени). Синтетический legacy STOP больше не рассылается: активные каналы требуют versioned policy media, а очередь компаньона сама закрывается при потере отправителя.

### Обработка пакета

На `on_tick` мод вызывает `helpers.recv_udp()`. Обработчик `on_udp_packet_received` проверяет `R,1` и длину, а отправителем считает `event.player_index` (0 — сервер). HELLO регистрирует возможности компаньона и возвращает ROSTER, POLICY, `MIC_STATE` и `HALF_DUPLEX`; у регистрации хаба отдельная ветка. SIGNAL пересылается адресату независимо от голосовых прав. Для START3/VOICE3/STOP3 до изменения HUD проверяются TX, ревизия и идентичность разговора; legacy/v2-медиа активный мод отбрасывает.

`fan_out(sender, kind, payload, previous)` вставляет индекс отправителя и пересылает policy-медиа только допустимым получателям с `pol1`, при старой смежной ревизии — пересечению политик. Собственная копия требует self-monitor. `helpers.send_udp(port_q, data, q.index)` фактически отправляет только из копии игры получателя. `port_q` берётся из синхронизированной per-user настройки `ptt-radio-companion-port` (по умолчанию 34555).

Область вещания задаёт map-настройка `ptt-radio-scope`: `all` (по умолчанию) или `force` (только своя команда). Это внешняя граница для каналов, её прежний смысл и значение по умолчанию сохранены.

### Каналы и политика воспроизведения

`channels.eligible(sender, listener)` определяет игровые копии, HUD, щелчки и множества POLICY. ANY — общий канал по умолчанию, не wildcard. RX состоит из TX, дополнительных подписок и обязательного админ-канала, пока рация включена. «Здесь» сравнивает `physical_surface`; событие просмотра другой поверхности при неизменной физической поверхности не меняет ревизию. Обычный `SignalID`, включая сигнал планеты, задаёт статический канал. Серверная политика может запрещать передачу/приём, глушить передатчик и ограничивать выбор. Полудуплекс глушит весь вывод при удержанном PTT, включая админ-канал; исключения с приоритетным звуком нет.

`channels.tx_permitted` отдельно проверяет присутствие, off, mute, TX-deny и право вещания на админ-канале. RX-only deny не выключает передачу другим слушателям. POLICY bit 0 приходит из этой проверки; bit 1 дополнительно требует собственное эхо и self eligibility. Пустой send set не означает mute. При off очищены оба множества и оба флага. Правило off для источника 0 сохранено, но нынешний хаб — только сигнализация и непрозрачный relay, он не производит звук. Его пятибайтовый HELLO не объявляет медиавозможность; серверному источнику звука в будущем нужен отдельный явный контракт регистрации.

Живые каналы требуют токен `pol1` в HELLO. Старые компаньоны исключены из медиамножеств и не получают legacy/v2 копий; окно настроек предлагает обновление. При этом подходящие по каналам зрители видят HUD и слышат игровые щелчки даже без компаньона или со старой версией: для них сохраняется отдельный снимок eligibility. SIGNAL и регистрация хаба работают независимо от медиаправ. Каждая изменившаяся глобальная ревизия уходит всем подключённым `pol1` компаньонам, включая неизменившихся получателей. Ревизия хранится как восемь байт, перенос считается побайтно; переполнение отвергается. Идентичный HELLO не меняет ревизию или существующие HUD-элементы.

Повторный HELLO при неизменных присутствии и `pol1` отправляет сохранённый POLICY без пересчёта пар игроков и не перестраивает открытое окно настроек: черновик, выбор сигнала и прокрутка остаются на месте. Изменение только `hud1`, `v2` или строки версии не затрагивает настройки и POLICY; потеря возможности HUD по-прежнему очищает измерения этого зрителя. Повышение и понижение администратора сразу пересчитывают права админ-канала и обновляют открытые элементы администрирования.

Версия мода 0.4.0 мигрирует сохранения 0.2.0 и 0.3.0: сохраняет радио, политику и личную панель эха, но удаляет старые активные разговоры и заново строит снимок. Если сохранение без новых таблиц загружено без события конфигурации, первый доступ из записываемого обработчика выполняет ту же инициализацию. В `on_load` записей нет; последующие события проверяют только маркер инициализации, без повторного обхода игроков.

Мод хранит неизменяемые снимки текущей и предыдущей политики. Предыдущая используется только при числовой смежности и разрешении пары в обеих политиках, self — с обоими наборами TX/self флагов. Будущие и пропущенные эпохи не угадываются. До изменения generation/talkspurt/HUD проверены формат, длина, capability, TX и ревизия. HUD хранит членство слушателей после принятых пакетов: старый START не открывает строку новому слушателю, старый STOP снимает её только для разрешённого пересечения. Отзыв удаляет это членство и link state; повторное разрешение ждёт нового принятого голоса. Значок канала меняется на месте первым текущим пакетом после смены TX, без перестановки строки и сброса качества.

Каналы регулируют воспроизведение у честных клиентов, а не конфиденциальность: игровой Opus остаётся реплицированным input action и доступен изменённому клиенту. Границы лабораторных измерений и wire-схема приведены в Companion policy transitions ниже.

### Плашка, звуки, клавиши

- **Плашка.** Стопка строк в `gui.screen` у левого края, на 40 % высоты; правый край занят панелью информации о сущности: значок TX-канала, имя в `chat_color`, качество или метка эха. Новый разговор получает место в конце, повторы его не переставляют; принятый STOP и таймаут убирают строку. Переполнение показывает «ещё N», разрешение и масштаб пересчитывают вместимость. Своя визуальная строка не требует self-monitor звука, но требует разрешённую передачу и channel eligibility.
- **Источник эха.** Компаньон шлёт `ECHO_STATE` (`0x05`) при обнаруженном пути динамики → микрофон. Флаг `storage.echo_sources` заменяет качество меткой эха только в активной строке; молчащий источник не создаёт HUD-строку. Личная панель в `gui.left` показывает предупреждение и кнопку выключения открытого микрофона; при уже выключенном микрофоне кнопка скрыта. Флаг и панель снимаются при `ECHO_STATE 0`, потере компаньона или выходе игрока. В чат обнаружение эха не печатается.
- **Щелчок рации.** `player.play_sound` у подходящих слушателей при открытии и закрытии принятого разговора, без участия компаньона. Используются встроенные `utility/gui_click` и `utility/list_box_click`; отдельные звуковые прототипы в `data.lua` не создаются.
- **Переключатель открытого микрофона.** Кнопка `ptt-radio-open-mic` на панели быстрого доступа (`shortcut`, `toggleable`) и клавиша `custom-input` `ptt-radio-toggle-mic`, по умолчанию `ALT + V`. В v0.1 стояла `ALT + T`, но в 2.1 она открывает экран технологий. Желаемое состояние хранится в `storage.open_mic` и показывается подсветкой кнопки (`set_shortcut_toggled`). Компаньону уходит `MIC_STATE` с явным байтом состояния, а не «переключи»: так перезапущенный компаньон не расходится с кнопкой. Удержание PTT ловит компаньон, потому что `custom-input` не сообщает об отпускании, а `associated_control_input` у кнопки только подписывает клавишу в подсказке.
- **Присутствие компаньона.** Компаньон шлёт HELLO раз в 5 с всё время работы. Мод хранит тик последнего HELLO в `storage.companions`. На каждый HELLO он отвечает ростером, `MIC_STATE` и `HALF_DUPLEX`, а при первом HELLO пишет игроку «компаньон подключён». После 15 с игрового времени без HELLO мод считает компаньон пропавшим: снимает открытый микрофон и пишет об этом игроку. Нажатие кнопки без живого компаньона ничего не переключает и объясняет, что запустить. Отличить «компаньон не запущен» от «игра без `--enable-lua-udp`» мод не может: без флага `send_udp`/`recv_udp` молча ничего не делают.
- **Запасной путь удержания на чистом Lua (не реализован).** Selection-tool с `send_pre_selection_events`: `on_player_start_selected_area` срабатывает на нажатие ЛКМ, `on_player_selected_area` на отпускание. Пригодится на Wayland, где глобальной клавиши может не быть. Документация предупреждает, что эти события стоят производительности в мультиплеере, поэтому возможное добавление требует отдельного решения.

## Формат пакетов

Lua 5.2 в Factorio не имеет `string.pack`, поэтому заголовок фиксированный и разбирается через `string.byte` и `string.char`. Тело для мода непрозрачно: двоичные Opus-кадры с `\0` проходят без искажений (проверено).

Активное медиа компаньон → игра (`127.0.0.1:<порт --enable-lua-udp>`), индексы байтов с нуля:

| Байты | Поле |
|---|---|
| 0–2 | `0x52, 1, kind`: START3 `0x0b`, VOICE3 `0x0c`, STOP3 `0x0d` |
| 3–4 | номер кадра u16 big-endian |
| 5–12 | поколение потока u64 big-endian |
| 13–14 | talkspurt u16 big-endian |
| 15–22 | ревизия POLICY u64 big-endian |
| 23… | Opus только у VOICE3, 1–1156 байт |

START3 и STOP3 имеют ровно 23 байта. Игра вставляет `sender_index u16` сразу после типа: входящий заголовок медиа — 25 байт. POLICY (`0x15`), SIGNAL и зашифрованные UDP-пакеты имеют отдельные схемы в [P2P contracts](#p2p-transport-contracts-v2-2026-10-24) и [Companion policy transitions](#companion-policy-transitions).

Базовый legacy-заголовок, сохранённый в `packet.rs` для управляющих сообщений и совместимости компаньона:

| Байты | Поле |
|---|---|
| 0 | `0x52` (`R`) |
| 1 | версия протокола, `1` |
| 2 | тип: `0x01` HELLO, `0x02` START, `0x03` VOICE, `0x04` END, `0x05` ECHO_STATE |
| 3–4 | номер кадра, u16 big-endian (для VOICE; в START/END — номер последнего; для ECHO_STATE `0`) |
| 5… | тело: Opus-кадр для VOICE, версия компаньона для HELLO (с токеном ` v2` у компаньона с v2-медиа), один байт для ECHO_STATE |

`HELLO`: тело — строка версии и отдельных whitespace-токенов возможностей. Текущий компаньон отправляет `ptt-radio-companion <ver> hud1 pol1 v2`; мод разбирает токены независимо от порядка. `pol1` разрешает участие в активном медиаконтракте, `hud1` — отчёты качества. Возможности обновляются каждым HELLO и снимаются при потере компаньона; их изменение пересчитывает политику. Пятибайтовая регистрация хаба (игрок 0) не объявляет эти возможности. Таблицы базовых legacy-пакетов здесь описывают сохранённую совместимость компаньона; активный мод принимает только START3/VOICE3/STOP3, чья полная схема приведена ниже.

`ECHO_STATE`: тело — один байт, `0` эха нет, `1` эхоподавитель компаньона включён на найденном пути динамики → микрофон этого игрока. Компаньон шлёт его при каждой смене и вместе с каждым HELLO (раз в 5 с). Мод игнорирует тело иной длины и иные значения, а также `ECHO_STATE` от компаньона, не приславшего HELLO: снять такой флаг было бы нечему. Версия протокола остаётся `1`.

Игра → компаньон (`127.0.0.1:<ptt-radio-companion-port>`): тот же заголовок, после байта типа вставлен `sender_index` u16 big-endian. Типы ответа: `0x02`/`0x03`/`0x04` пересланные, `0x10` ROSTER (строки `index\tname\tr,g,b`), `0x11` MIC_STATE (тело — один байт: `0` открытый микрофон выключен, `1` включён; компаньон выставляет ровно это состояние), `0x12` HALF_DUPLEX (тело — один байт: `0` выключен, `1` включён; настройка игрока `ptt-radio-half-duplex`). MIC_STATE и HALF_DUPLEX уходят только компаньону самого игрока: на каждый HELLO и при смене состояния. Новый тип не меняет версию протокола: старый компаньон отбрасывает неизвестный тип, а новый до первого HELLO-ответа считает полудуплекс включённым, как и настройка по умолчанию.

Один Opus-кадр на пакет: 20 мс по умолчанию, 10 мс с `--frame-ms 10`. Длину кадра приёмник узнаёт от декодера, поэтому формат её не несёт, а говорящие с разными кадрами смешиваются. Пакеты всё равно приходят пачками по тику, поэтому объединять кадры имеет смысл только после замера накладных расходов на input action.

## Компаньон

Язык: Rust. Основной поток обслуживает глобальную клавишу, heartbeat и жизненный цикл микрофона; рабочие потоки занимаются передачей, приёмом и воспроизведением. Callback `cpal` передаёт сэмплы через очереди. Игровой сокет по умолчанию — `127.0.0.1:34555`; UDP-пути используют отдельные привязанные интерфейсы. Подробная карта модулей и потоков — в [ARCHITECTURE.md](ARCHITECTURE.md).

Cargo по умолчанию включает `audio` и `self-update`. `audio` нужен бинарникам `ptt-radio-companion` и эмулятору `relay`; `ptt-radio-hub` собирается с `--no-default-features`, без аудиоустройств, Opus/AEC и самообновления.

Сборка компаньона с `self-update` проверяет обновление при старте до сокетов, аудио и клавиши, только если при компиляции задано `PTT_RADIO_RELEASE_BUILD=1` (release workflow). Обычный локальный `cargo build`, включая `--release`, себя не заменяет. Проверка GitHub Releases выбирает строго более новую стабильную версию, проверяет архив по `SHA256SUMS`, извлекает исполняемый файл, заменяет его и перезапускает с прежними аргументами. Ошибка проверки или установки оставляет текущую версию для запуска; результат печатается в stderr. `--no-self-update` или `PTT_RADIO_NO_SELF_UPDATE=1` отключают проверку. После успешной замены маркер перезапуска предотвращает повторную проверку в новом процессе.

### Передача

- 48 кГц моно, Opus `VOIP`. По умолчанию кадр 20 мс (960 сэмплов), 16 кбит/с, сложность 9, FEC и DTX выключены; выбор обоснован развёрткой качества ниже. Флаги `--frame-ms 10|20`, `--bitrate`, `--complexity 0..10`, `--fec` меняют их для замеров.
- По нажатию PTT при разрешённой передаче: START3, затем до 120 мс уже записанного звука (pre-roll: до 6 кадров по 20 мс или 12 по 10 мс, включая текущий), затем VOICE3. Сразу после открытия микрофона или сброса pre-roll накопленного звука меньше.
- По отпусканию, если открытый микрофон выключен: закончить текущий кадр, отправить STOP3 дважды. Слушатель выпускает ожидающие сжатые кадры и доигрывает остаток PCM; мгновенная тишина на стороне слушателя не гарантируется.
- Порт игры задаётся `--game-port` (по умолчанию 34556) и должен совпадать с `--enable-lua-udp`: из игры его узнать нельзя. Если ROSTER не пришёл за 3 с, компаньон предупреждает о возможном неверном порте, отсутствии флага, мультиплеера или мода и продолжает попытки. HELLO повторяется каждые 5 с, пока компаньон работает: это heartbeat, по которому мод показывает игроку, жив ли компаньон.
- PTT-клавиша по умолчанию — `F8`. На macOS `global-hotkey` регистрирует Carbon-хоткей, который съедается во всей системе, поэтому буква сломала бы набор текста. `F8` не занята ни в Factorio 2.1, ни обычно в системе. Кнопки мыши и одиночные модификаторы требуют слушающего `CGEventTap` с разрешением Input Monitoring; в v0.1 этого нет.
- Открытый микрофон (по `MIC_STATE` = 1) передаёт так же, как удержанный PTT, пока POLICY разрешает TX.

Физический микрофон начинается закрытым. Он открывается при установленном POLICY с TX и последнем принятом обновлении моложе 60 с; идентичный POLICY тоже продлевает срок. При разрешённой рации устройство остаётся открытым и между нажатиями PTT для pre-roll. Off, mute, запрет TX или истечение 60 с без принятого POLICY закрывают его. Пустой send set сам по себе не запрещает захват. На паузе игры обновления POLICY стоят, поэтому физический микрофон через 60 с закрывается даже при работающем UDP-пути.

Перед освобождением устройства компаньон завершает текущую передачу и выпускает два STOP под прежними правами, затем отсоединяет захват и меняет его поколение. После освобождения сбрасываются AEC и ECHO_STATE; передатчик при новом поколении очищает прежний pre-roll. Сэмплы прежнего открытия не могут попасть в новую передачу. При восстановлении прав заново выбирается текущий системный микрофон по умолчанию; ошибка открытия не завершает процесс, повтор — через 1 с. Тон и WAV остаются синтетическими источниками для тестов, их pre-policy совместимость не означает разрешение физического захвата.

### Приём

- **Порядок до декодера** (`src/reorder.rs`, контракт `PreDecodeOrder` из раздела P2P ниже). У каждого говорящего один поток: стадия упорядочивания сжатых кадров, один декодер Opus и очередь PCM. Кадр, продолжающий поток, декодируется в момент прихода, без ожидания. Ждёт только кадр за пропуском, не дольше `REORDER_MS` (`reorder::GAME_ONLY.wait`) = 10 мс от своего прихода; затем пропуск один раз маскируется (FEC из следующего кадра, если он есть, иначе PLC декодера), а опоздавший кадр и повторы отбрасываются (`discarded` в итоге). 10 мс — начальная политика упорядочивания (разница задержек двух путей плюс 10 мс) при единственном пути через игру: разница 0. Потери и перестановки возможны и на игровом пути. Runtime пересчитывает срок по измеренной разнице путей, сохраняя очередь и декодер. Очередь стадии ограничена 20 кадрами (200 мс кадров по 10 мс, столько же держит очередь PCM); при переполнении пропуск закрывается сразу. Из длинного пропуска (скачок номера) маскируются только последние `reorder::MAX_CONCEAL` = 5 кадров, 100 мс кадров по 20 мс, последний по-прежнему с FEC. Остальные пропускаются без декодера: очередь PCM больше 200 мс не держит, а если она опустеет, маскирует сама по срезу за такт. Без этой границы скачок на 32766 кадров стоил бы столько же вызовов PLC подряд, около 300 мс в одном такте. Копии пропущенных кадров отбрасываются как опоздавшие. Срок проверяют приход пакета и каждый такт микшера (10 мс). STOP выпускает всё, что ждёт за пропуском.
- **Идентичность.** Пакеты v1 (START/VOICE/STOP) идут в тот же поток с поколением 0: v1 его не несёт, поэтому каждый START начинает нумерацию заново (перезапущенный компаньон снова считает с 1). START2/VOICE2/STOP2 (`0x07`–`0x09`) декодируются только после выбора поколения доверенной сигнализацией (`ANNOUNCE`, `Mixer::select`). До этого игровой приём хранит одно ожидающее поколение игрока: до 20 записей не старше 200 мс, максимум для 256 игроков; совпавшие записи при выборе выпускаются в порядке разговора и номера, остальные удаляются. После выбора копии v1 этого игрока отбрасываются. Новое поколение — перезапуск компаньона: прежний поток, декодер и очереди удаляются сразу, пакеты старого поколения ничего не выбирают и не играют. Разговор (`talkspurt`): повторный START открытого разговора ничего не меняет (`Stream::restart`, без перебуферизации), всё от более старого или уже закрытого разговора отбрасывается, START или VOICE нового разговора открывает его, даже если START потерян. STOP принимается только для открытого разговора с его номером и закрывает его. Любой другой STOP (старше, уже закрытого или новее открытого) отбрасывается и ничего не меняет. Более новый STOP не запоминается: по нескольким путям он может обогнать голос своего разговора, и тогда этот голос играет, а поток закрывается по тишине очереди PCM (300 мс), как при потерянном STOP. Порядок и декодер выбранного потока переживают такое закрытие очереди PCM. Поэтому копия уже сыгранного кадра, пришедшая позже по другому пути, остаётся повтором, а новый кадр того же разговора играет сразу. Новый разговор после закрытия начинает поток заново, как первое нажатие: кадры прежнего разговора и так отбрасываются, а скачок номера между нажатиями не ждёт и не маскируется. Состояние разговора забывается через 60 с тишины этого потока; следующий кадр после этого тоже начинает поток заново. У v1 поток удаляется вместе с очередью PCM, как раньше. После POLICY runtime передаёт START3/VOICE3/STOP3 с ревизией; активный мод legacy/v2-медиа не пересылает. Legacy-приём и v2-кодеки сохранены для совместимости и тестового эмулятора. До POLICY физический микрофон закрыт. HELLO с `hud1 pol1 v2` отправляется до запуска медиапотоков, но порядок прихода по сети не гарантирован.
- Отдельная очередь на каждого говорящего. Пакет декодируется сразу, как его выпустила стадия порядка, и ложится в очередь срезами по 10 мс: кадр 20 мс даёт два среза, кадр 10 мс один. Микшер и вывод работают тактом 10 мс независимо от кадра отправителя. Воспроизведение начинается, когда накопилось 40 мс или прошло 60 мс после `START`.
- Если в очереди больше 200 мс (пачка после автосохранения), лишнее выбрасывается до целевой глубины. Догонять, проигрывая подряд, нельзя.
- **Сброс лишнего запаса.** Очередь помнит свою глубину после каждой выборки за последние 20 выборок (200 мс, два периода узора «тик 60 Гц против кадра 20 мс»). Наименьшая из них — срезы, которые неравномерность доставки ни разу не понадобилась: хвост пачки pre-roll или пачки после остановки. Из них очередь всегда оставляет 10 мс запаса, остальное микшер пропускает по одному срезу: сначала тихий (уровень ниже 10 % от скользящего уровня голоса), а если запас держится дольше 400 мс — и речевой. Пропуск сглажен переходом 2,5 мс от текущего среза к следующему. Выбор между выбросом и сжатием времени — в пользу выброса: в паузах между слогами его не слышно, а сжатие времени меняет тембр и требует отдельного алгоритма. Запас 10 мс найден пробой: без него очередь пустела раз на фразу (пачка по тику приходит раз в 16,7 мс, а такт 10 мс), с ним ни разу, а задержка та же. После провала очередь 5 с держит 20 мс запаса, чтобы следующая пачка не вызвала новый провал.
- По STOP доиграть остаток и закрыть очередь PCM. При опустошении очереди посреди передачи декодер Opus достраивает пропущенные 10 мс из своего состояния (PLC) вместо паузы: причиной могут быть как неравномерность, так и потеря.
- Микшер суммирует потоки и применяет мягкое ограничение `tanh`. ROSTER задаёт имена и цвета; индивидуальная громкость и полосовой «эффект рации» в микшере не реализованы.
- **Полудуплекс.** Пока игрок держит PTT, его динамики молчат, как у настоящей рации: микрофону нечего вернуть в эфир. Настройка игрока `ptt-radio-half-duplex`, по умолчанию включена; в наушниках её можно выключить и слышать собеседников во время своей речи. Глушится только вывод, приём и декодирование идут дальше, поэтому после отпускания звук продолжается с того же места, без провала и без сдвига задержки. Переход сглажен рампой 5 мс в обе стороны. Открытый микрофон полудуплекс не трогает: глушить динамики всё время, пока он включён, значит не слышать никого. Опорный сигнал подавителя эха получает то, что реально звучит, то есть тишину, пока вывод заглушён. В трассе `mute <0|1> <сэмпл>`: начало и конец глушения на шкале устройства.
- **Эхо-режим.** Мод пересылает пакет и самому отправителю. Это проверка всего тракта (микрофон → Opus → сервер → декодер → динамик) на одной лицензии.

### Клавиша и права ОС

- **macOS (первая платформа).** `global-hotkey` сообщает `HotKeyState::Pressed` и `Released`. Захват микрофона требует `NSMicrophoneUsageDescription`, а в подписанной сборке ещё и entitlement `com.apple.security.device.audio-input`. Мышиные кнопки как PTT требуют `CGEventTap` и права Input Monitoring. Непроверенное: что `global-hotkey` на macOS обходится без Input Monitoring, и что неподписанная сборка, запущенная из терминала, наследует права терминала.
- **Windows.** `global-hotkey` использует `RegisterHotKey`. Основной поток, создавший manager, ждёт сообщения через `MsgWaitForMultipleObjects` и обрабатывает очередь `PeekMessageW` → `TranslateMessage` → `DispatchMessageW`; без этой помпы события скрытого окна `WM_HOTKEY` не доходят до PTT.
- **Linux.** X11 через `global-hotkey`. На Wayland нужен портал GlobalShortcuts (`Activated`/`Deactivated`) или запасной путь через selection-tool в моде.

### Эхо от динамиков

Игрок с динамиками и открытым микрофоном возвращает в эфир всё, что слышит, и остальные слышат себя с задержкой около полсекунды. С PTT это закрывает полудуплекс (см. «Приём»), с открытым микрофоном он не помогает. `src/echo.rs` обрабатывает render по 10 мс (48 кГц, вместе с тишиной и заглушённым полудуплексом выводом) и каждый захваченный кадр перед кодированием. Подавитель адаптируется непрерывно, но его выход выбирается только после обнаружения акустической связи: политика и ограничения описаны в разделе AEC ниже. Пока связь найдена, компаньон шлёт моду `ECHO_STATE` = 1, и мод показывает игрока источником эха (см. «Плашка, звуки, клавиши»). Опора отдаётся примерно на глубину очереди вывода раньше, чем звучит (~17 мс), а захваченный кадр доходит до AEC через кадр плюс буфер захвата.

### Проверка индикатора эха без аудио

Из корня проекта сначала выполнить `uv run -q tools/radio.py hello`, затем в течение 15 с отправить `ECHO_STATE` в Lua UDP-порт своего клиента. Для порта 34556 включение: `printf '\x52\x01\x05\x00\x00\x01' | nc -u -w1 127.0.0.1 34556`; выключение: `printf '\x52\x01\x05\x00\x00\x00' | nc -u -w1 127.0.0.1 34556`. Если клиент запущен с другим `--enable-lua-udp`, заменить порт в командах и передать тот же порт эмулятору через `--game-port`. Без HELLO мод не принимает `ECHO_STATE`; без новых HELLO флаг снимается через 15 с вместе с записью компаньона. Это проверка индикации мода, а не качества обнаружения акустического эха; работающий компаньон сам шлёт `ECHO_STATE` при включении эхо-гейта.

## Сквозной стенд без игры

Весь голосовой тракт проверяется без Factorio. Игру и мод заменяет эмулятор, компаньон запускается без изменений, по одному процессу на игрока, а звук идёт через виртуальное устройство.

- **Эмулятор игры** (`src/relay.rs`, бинарник `relay`). У каждого игрока свой игровой порт, куда шлёт его компаньон, и порт компаньона. Формат пакетов тот же, что у `control.lua`: на HELLO приходят ROSTER от игрока 0, `MIC_STATE` и `HALF_DUPLEX` с индексом самого игрока (полудуплекс в эмуляторе по умолчанию выключен, флаг `--half-duplex <индекс>`), START/VOICE/STOP пересылаются остальным с индексом отправителя, себе только при включённом эхо. Эмулятор сохраняет pre-policy мост START2/VOICE2/STOP2 (`0x07`–`0x09`): индекс встаёт перед номером, поколением и разговором. Каждый получатель этого моста получает одно представление отправителя: компаньон с токеном ` v2` в HELLO — v2, старый — v2, переведённые в v1 (см. «The outer game magic/version remain `R,1`»). Модель транспорта воспроизводит локальный прогон клиента macOS и сервера Linux в виртуальной машине: задержка 72 мс плюс случайные 0–10 мс, доставка на ближайшем тике 60 Гц, без потерь и перестановок. Получается p50 ~85 мс и p95 ~95 мс «клиент → сервер → клиент». Остановка (автосохранение) прекращает тики, накопленное приходит пачкой на первом тике после неё. Эмулятор сохраняет legacy-синтетический STOP и область `force`; активный мод вместо legacy-медиа требует POLICY и START3/VOICE3/STOP3. Тесты policy-переходов подают POLICY и versioned media отдельно.
- **Виртуальное звуковое устройство** (`src/virtual_audio.rs`, флаги `--mic-wav`, `--speaker-wav`). Поток раз в 10 мс делает то же, что callback `cpal`: кладёт в очередь захвата кусок WAV в реальном времени (после конца файла тишину) и забирает кусок из очереди вывода в WAV, тишину тоже. Остальной компаньон работает как с настоящими устройствами. Связь «динамик → микрофон» (`--couple-gain-db`, `--couple-delay-ms`, `--couple-ir`) подмешивает собственный вывод в микрофон с задержкой, усилением и импульсной характеристикой. Это и есть игрок с динамиками. Настоящие устройства добавляют свою задержку ввода-вывода, виртуальное её не моделирует.
- **Трасса** (`--trace`). Компаньон пишет параметры кодека (`codec <сэмплов в кадре> <бит/с> <сложность> <fec>`) и время каждого кадра: готовность и отправку с номером захваченного кадра и размером пакета, приём, выборку каждого 10-мс среза (`pull <отправитель> <номер кадра> <смещение среза в кадре> <глубина> <сэмпл>`) с глубиной очереди и номером сэмпла на шкале устройства, с которого звучит срез (счёт устройства и длина очереди читаются под одной блокировкой, поэтому момент воспроизведения точен, а не выведен из границ периодов). Эмулятор сам отмечает приём и доставку. Время везде настенное, поэтому процессы сводятся на одну шкалу.
- **Сценарии** (`tests/scenarios.rs`). Голос — синтетический, похожий на речь: гармоники плавающей основной частоты под двумя формантами, часть слогов шумовые, паузы между слогами и фразами. Вместо него можно подставить свой WAV. Задержку «рот–ухо» дают взаимная корреляция огибающих (1 мс) входа говорящего и выхода слушателя и, независимо, сумма этапов по трассе. Разница между ними — задержка кодека. Уровни считаются по энергии, в двойном разговоре — подбором МНК двух сдвинутых огибающих мощности.

### AEC только при обнаруженном эхо

По умолчанию `--aec on`: микрофон идёт без изменения сэмплов, пока детектор не обнаружил связь вывода с микрофоном. `--aec off` полностью отключает обработку и детектор. Кодековая развёртка ниже всегда запускается с AEC off. Тест собственного возвращённого тона тоже требует `--aec off`: совпадающий с микрофоном возвращённый сигнал детектор не может отличить от акустического эха.

Подавитель — stock `sonora = 0.2.0`, AEC3 с `TransparentModeType::Hmm`; NS и AGC выключены. Это Rust-код, без системного WebRTC. Opus остаётся статическим bundled libopus. Render берётся после микширования из реально отправляемых на устройство 10-мс срезов. AEC работает на рабочих потоках, вне callback `cpal`, и адаптируется даже при сухом выходе. Очередь render ограничена двумя блоками и со стороны производителя: при остановке захвата старый блок сразу обрабатывается; возобновление захвата не разгребает неограниченную очередь.

Сухой путь не задерживается. На мокром измерено 436 сэмплов (9,083 мс) при трёх фазах импульса; переключение смешивает пути за 10 мс. Разница задержек даёт локальный разрыв/повтор формы волны; crossfade смягчает его, но не устраняет. `aec_gate` в трассе содержит состояние, score, lag и индекс сэмпла захвата, с которого начинается переход. Следующая строка `canceller` задаёт 0 либо 9,083 мс для этого интервала. Анализ выбирает применимый интервал каждого переданного кадра, а не первую/последнюю строку файла; окна перехода исключены из спектрального замера.

Детектор сравнивает render и сырой capture: усреднение до 2 кГц и разность соседних отсчётов, окно 160 мс, поиск задержки до 1 с, обновление каждые 100 мс. Знаковая ковариация накапливается с коэффициентом 0,8 по одной задержке. Для входа нужны score ≥0,20, изолированный пик (в 1,4 раза выше боковых пиков за пределами ±3 мс) и три совпадения задержки в пределах 2 мс. При score ≥0,8 достаточно двух; иначе первые 500 мс служат накоплению. Это консервативный выбор по замерам независимых голосов: более быстрые пороги ложно включались на гармониках голоса в наушниках.

Есть второй путь входа, для сильного эха с неизолированным пиком: score ≥0,75 и пик в 1,4 раза выше той части боковых пиков, которую не объясняет автокорреляция самого render. Нужен он из-за открытых микрофонов на колонках у нескольких игроков (многопользовательская эхо-лаборатория, сценарий a). Там один пик не изолирован ни при каком правиле, и на то есть две причины:
- период основного тона далёкого голоса (около 4,5 мс) даёт гребёнку боковых пиков;
- голос, вернувшийся через чужие колонки, повторяется в render через 400–600 мс.

Детектор раньше оставался сухим, и петля выла так же, как без подавителя. Остаток считается так: из корреляции вычитается пик, умноженный на нормированную автокорреляцию render на том же сдвиге. Высокий порог score не пускает этот путь на голоса в наушниках, у которых корреляция по гармоникам слабая. Сам по себе высокий score ничего не говорит о направлении. Вокализованный ближний голос, который возвращается в render через чужой микрофон, коррелирует и на коротких прямых задержках. Поэтому второй путь требует ещё одного: корреляция в обратную сторону должна быть ниже прямой. Обратная — это когда capture опережает render, новейшее окно render сравнивается с историей capture за 1 с. Настоящий путь прямой, и прямая корреляция у него выше, а у вернувшегося голоса выше обратная. С этим проходят `headphones_matrix`, тесты собственного голоса (шумового и вокализованного), вернувшегося в render, и многопользовательская эхо-лаборатория (сценарий a без воя).

Обнаруженный путь сохраняется через тишину и через независимый близкий голос, маскирующий эхо. Отсутствие корреляции считается отрицательным свидетельством только при активном render и когда микрофон достаточно тих, чтобы ожидаемое эхо было наблюдаемо. Десять таких обновлений с мгновенным score <0,15 выключают путь; положительное совпадение сбрасывает счётчик. Поэтому смена динамиков на наушники во время непрерывной громкой речи может определиться только в более тихом участке. Путь не переключается на каждой удалённой фразе, сохраняя обработку хвоста комнаты.

Офлайн-лаборатория `tests/aec_gate.rs`: два независимых речевых WAV 48 кГц, 60 с с повтором, прямой путь 20 мс и затухающий хвост 150 мс. Холодный старт — оба говорят с начала; прогретый — ближний голос начинается через 3 с. Начало дальней речи определяется по 10-мс RMS >−70 dBFS (в этих файлах 0 мс). Уровни ниже — в микрофоне до включения; −6/−20/−30 дБ — коэффициент прямого пути, не полная энергия комнаты.

| путь | включение, холодный | утечка до включения, dBFS / к ближнему голосу | включение с 3 с прогрева | переключений за 60 с |
|---|---|---|---|---|
| наушники | не включился | эха нет | не включился | 0 |
| −6 дБ | 690 мс | −24,5 / −10,0 дБ | 690 мс | 1 |
| −20 дБ | 16 390 мс | −39,0 / −20,8 дБ | 690 мс | 1 |
| −30 дБ | 32 290 мс | −48,6 / −30,6 дБ | 690 мс | 1 |

Слабый путь при непрерывной ближней речи долго остаётся сухим: это измеренная утечка, а не гарантия её неслышимости. Ещё восемь 60-секундных прогонов наушников (оба порядка голосов, начало ближнего 0/3 с, вызовы 10/20 мс) ни разу не включились; каждый float-сэмпл совпал с входом. Это покрытие двух голосов, не доказательство для любой речи/музыки. Обработка 60 с в лаборатории заняла ~1,6–1,8 с настенного времени на этой машине; CPU и RT-нагрузка отдельно не профилировались.

Метрика ближнего голоса отделяет известные исходники near и реального комнатного echo комплексной регрессией 2×2 для каждого спектрального бина. STFT: окно 10 мс, коэффициенты на скользящих 100 мс, полосы <1 / 1–4 / 4–8 кГц. Измеренная задержка учитывается в фазе; плохо обусловленные смеси исключаются (condition >100), доля исключений печатается. Отдельно выводятся потеря near, остаток echo и необъяснённое искажение. Контроли: тождественный выход, идеальное удаление echo, echo ×0,1, удаление near выше 1 кГц, коллинеарные исходники и задержка 436 сэмплов. Общая потеря энергии смеси не называется потерей голоса.

**Ограничение динамиков:** gate защищает наушники, но не исправляет спектральное повреждение ближней речи внутри AEC3 при двойном разговоре. В прогретом −6 дБ случае на участке 10–60 с оценка потери near составляет 4,67 / 9,59 / 11,67 дБ по трём полосам; остаток echo снижается на 48,5 / 65,6 / 64,9 дБ. При холодном старте near теряет 5,72 / 11,74 / 14,99 дБ на том же участке. Регрессия описывает когерентную составляющую, не заменяет прослушивание. WAV и спектрограммы сохраняют исходную громкость; спектрограммы подтверждают провалы верхних гармоник. Пользователь ещё не принял качество этих файлов.

`ECHO_STATE` (`0x05`, seq=0, тело один байт 0/1) уходит в игру на смене состояния gate и вместе с каждым HELLO. Это состояние обнаруженного пути, не индикатор мгновенной громкости. Эмулятор relay записывает отправителя и состояние; отображение и таймауты принадлежат моду.

### Развёртка кодека

`cargo test --release --test scenarios quality_sweep -- --ignored --nocapture`: A говорит с параметрами строки, B слушает с умолчаниями, по одному прогону на строку, синтетический голос. Качество сравнивается с исходником срез за срезом по трассе (номер кадра и смещение среза дают точное место в исходнике, поэтому сброшенные срезы не сбивают выравнивание): сегментное SNR после подбора задержки кодека и усиления и логспектральное расстояние (LSD) до 8 кГц на активных срезах. Абсолютные числа зависят от голоса, сравнивать стоит строки между собой. Байты — Opus плюс 5 Б заголовка, без накладных расходов input action. Во всех строках 0 выброшено и 0 маскировок.

| кадр, мс | кбит/с | рот–ухо, мс | пакетов/с | Б/с | segSNR, дБ | LSD, дБ |
|---|---|---|---|---|---|---|
| 20 | 12 | 152 | 50 | 1004 | 10,8 | 4,35 |
| **20** | **16** | **152** | **50** | **1582** | **11,4** | **4,10** |
| 20 | 24 | 152 | 50 | 2058 | 12,1 | 3,89 |
| 20 | 32 | 152 | 50 | 2695 | 11,4 | 3,76 |
| 10 | 12 | 142 | 100 | 1391 | 8,7 | 7,37 |
| 10 | 16 | 142 | 100 | 2126 | 11,0 | 4,30 |
| 10 | 24 | 142 | 100 | 2835 | 12,3 | 3,74 |
| 10 | 32 | 142 | 100 | 3315 | 12,3 | 3,57 |

Строки со сложностью 9. Сложность 10 даёт то же, что 9 (кроме 10 мс при 12 кбит/с). Сложность 5 в части строк хуже на 0,5–0,7 дБ SNR при той же задержке, но не везде. При 20 мс и 24 кбит/с независимый прогон дал 12,3 дБ против 12,1 у сложности 9, а при 32 кбит/с — 13,1 против 11,4. На этих метриках и синтетической речи сложность выше не обязательно лучше. Развёртка идёт с выключенным AEC, поэтому задержка подавителя в неё не входит. FEC (20 мс, 16 кбит/с) добавляет 2,5 % байтов и ничего не меняет: потерь в транспорте нет.

- Задержку меняет только длина кадра: 10 мс дают −10 мс, битрейт и сложность на неё не влияют.
- Кадр 10 мс удваивает число пакетов через Lua сервера и добавляет ~35 % байтов при том же битрейте (заголовок и накладные расходы Opus на кадр). При 12 кбит/с кадр 10 мс заметно теряет качество.
- 24 кбит/с лучше 16 на 0,7 дБ SNR и 0,2 дБ LSD за +30 % трафика, 32 кбит/с больше не прибавляет.

Умолчания остаются 20 мс, 16 кбит/с, сложность 9, без FEC. Кадр 10 мс стоит включать, когда в игре замерена цена 100 пакетов/с на говорящего для UPS сервера.

### Лаборатория эха на нескольких игроков

`PTT_LAB_A=… PTT_LAB_B=… PTT_LAB_C=… cargo test --release --test multiparty_lab -- --ignored --nocapture` (`tests/multiparty_lab.rs`, ~5 мин при шести строках подавителей). Это не сквозной стенд, а замкнутая петля в одном процессе: три игрока, шаг 10 мс, быстрее реального времени. Микрофон игрока слышит его голос, а у игрока с динамиками ещё и его собственный динамик через связь (усиление, 2 мс, комната из `scenarios.rs`; у игрока в наушниках связи нет). Динамик играет потоки остальных. Каждый поток проходит подавитель отправителя, кодер компаньона (`Transmitter` на открытом микрофоне, умолчания кодека) и декодер, а затем фиксированную задержку пути (умолчание `PTT_LAB_PATH=game`): пинг отправителя, 72 мс игры, округление до тика 60 Гц, пинг слушателя и 24 мс очереди приёма. Неравномерность по тикам и сброс запаса в лаборатории не моделируются, очередь вывода — один срез. Эхо ходит по кругу. Прогон с бегущей петлёй (динамик громче −10 dBFS за 0,5 с) останавливается, и в таблице пишется, когда петля убежала. Голоса — `say` (Milena, Eddy, Samantha), приведены к −24 dBFS на активной речи. Строки: `none` и `sonora-hmm` — стоковый sonora 0.2.0 с `TransparentModeType::Hmm` и опорой по блоку перед каждым блоком захвата (форма подавителя из `echo.rs`, перенесённая в тест). В `ROWS` также входят production `aec3-gate`, контроль `resample-only` и DTLN 128/512. «Холодный» прогон начинается сразу с расписания, «тёплый» — после 10 с, где каждый игрок по очереди говорит один, так что подавители остальных уже обучены на дальнем конце.

Метрика — подбор по полосам: STFT 1024/480, окна по 9 кадров (90 мс), в каждом бине комплексный МНК `Y = A·N + B·E + R` для потока говорящего против его чистого голоса `N` и эха на его микрофоне `E`, обе опоры сдвинуты на задержку подавителя (импульс: 436 сэмплов) и кодека (корреляция: 303). Задержка пути на подбор не влияет, поэтому потерю говорящего слышит одинаково любой слушатель. В строках: потеря в полосах <1, 1–4, 4–8 кГц — среднее по бинам и окнам `−20·log|A|`, взвешенное энергией `|N|²` (не отношение суммарных мощностей), с долей окон, где оно больше 6 дБ (дыры). Потеря бина ограничена 60 дБ, так что полностью вырезанный бин считается за 60 дБ. Окно входит в счёт по энергии опоры `N`, а не по выходу, поэтому полностью вырезанное окно тоже считается. Бин, где опоры почти коллинеарны (`|ρ| > 99/101`, число обусловленности нормированной матрицы Грама больше 100), пропускается: при ошибке округления `|ρ|` может дойти до 1 и выше. Подавление эха `−20·log|B|` берётся там, где эхо не тише ближнего конца на 10 дБ; искажения — `|R|²/|A·N|²`. На голосах лаборатории до замера проходят четыре контроля: тождество (0 дБ, искажения −89 дБ), полное удаление эха (B ниже −60 дБ), эхо −20 дБ (20,0 дБ во всех полосах), режекция выше 1 кГц только у `N` (0,0 / 56 / 60 дБ). Обычный `cargo test` на синтетических спектрах проверяет сам подбор:
- окно без изменений плюс полностью вырезанное: 30 дБ, 50 % дыр;
- всё вырезано: 60 дБ, 100 %;
- усиления 1 и 0,1 при равной энергии: 10 дБ, 50 %;
- `E = 3,3·N` точно и почти точно: все бины пропущены;
- коррелированное, но различимое эхо подбирается без пропусков. Собственное эхо — энергия голоса игрока, вернувшегося через микрофон другого, за первую реплику, которую никто не перекрывает; задержка — по корреляции огибающих рядом с расчётной.

Opus сам по себе (строка «только кодек») теряет 0,2 / 0,4–2,3 / 2,9–9,1 дБ. В полосе 4–8 кГц дырами оказываются 44 % окон у Samantha и 73 % у Milena, а у Eddy 4 %. Видимо, на 16 кбит/с кодек сохраняет в этой полосе огибающую, а не форму волны, и когерентный подбор видит это как потерю. Поэтому 4–8 кГц читаются только относительно этого пола, а не как абсолютная цифра. С полом кодека сравниваются строки подавителя.

**(а) Трое на динамиках, связь −6 дБ, пинги 20/60/120 мс, говорят один, двое, трое.** Без подавителя петля может завыть. Граница по модулю, без учёта фазы, на худшей частоте (970 Гц) даёт до +5,4 дБ за переход: столько было бы, если бы все пути сложились в фазе. Связь −6 дБ — энергия по всем частотам, а отражения комнаты на 970 Гц поднимают её до −0,6 дБ. Речь игрока доходит до двух слушателей. Что петля и правда неустойчива, показывает сама симуляция: петля убегает через 4,0 с после начала (в тёплом прогоне через 3,5 с прогрева) тонами 270 Гц и 1,3 кГц. С этой комнатой три открытых микрофона на колонках без подавления эха работать не могут. При ровной связи −6 дБ петля была бы на границе устойчивости, но у настоящей комнаты пики есть всегда. С `sonora-hmm` воя нет, собственное эхо в тёплом прогоне ниже −50 дБ; в холодном A слышит себя через C на −22,8 дБ и через B на −39,8 дБ, пока подавители учатся. Цена — ближний конец в двойном разговоре (тёплый прогон, потеря дБ / дыры):

Один говорящий почти не отличается от пола кодека. В двойном разговоре окна с вырезом больше 6 дБ занимают четверть–треть времени даже ниже 1 кГц и от пятой части до 73 % в 1–4 кГц, а средняя потеря у A и C доходит до 6–10 дБ. На спектрограмме это прямоугольные провалы по 0,1–0,3 с, в которых пропадают гармоники выше 1 кГц, иногда вся полоса. Подавление эха при этом 16–29 дБ, а в чистом дальнем конце 60–78 дБ ниже 4 кГц. Холодный прогон отличается только первыми секундами: подавление дальнего конца у B и C 22–40 дБ вместо 60–77.

**(б) A и B в наушниках спорят, C молчит с открытым микрофоном, колонки +6 дБ.** Без подавителя A и B слышат себя через C громче, чем говорят: +5,5 и +5,6 дБ через 522 и 616 мс. B к тому же слышит A дважды. С `sonora-hmm` в тёплом прогоне собственное эхо ниже −50 дБ, а подавление у C 90 / 74 / 59 дБ. В холодном A слышит себя на −8,4 дБ в среднем за первую реплику: две вспышки в первые 2 с, пока подавитель C не обучен, дальше тишина. Подавитель у игроков в наушниках (эха на их микрофонах нет) всё равно режет их речь в двойном разговоре. В тёплом прогоне при двойном разговоре у A дыры 13 / 18 / 86 % против 0 / 2 / 72 % без подавителя, у B 2 / 2 / 7 % против 0 / 0 / 3 %. Тот же дефект, что видели при проверке подавителя эха: в двойном разговоре AEC3 вырезает гармоники выше 1 кГц у ближнего конца, которого не нужно трогать.

Вывод: подавитель обязателен, как только на колонках больше одного игрока с открытым микрофоном. Стоковый AEC3 убирает эхо и вой, но в споре дырявит ближний конец на всех микрофонах, включая те, где эха нет. Последующий прогон production `aec3-gate` приведён в следующем разделе; он сохраняет dry у игроков в наушниках, но не устраняет потери ближней речи на engaged AEC.

### Сравнение DTLN в той же петле

В `multiparty_lab` к исходным строкам добавлены production `EchoPath` (`aec3-gate`), `Stream48` DTLN 128/512 и контроль `resample-only` через тот же `RateConverter`, без нейросети. Ни симуляция, ни контракт полосовой метрики не заменены. Нейросеть — только dev-зависимость: поведение компаньона не меняется. Модели, SHA-256, версия upstream и происхождение преобразования TFLite → ONNX описаны в [DTLN experiment](companion/experiments/dtln-runtime/README.md): breizhn/DTLN-aec `9d24e128b4f409db18227b8babb343016625921f`, MIT; отдельной лицензии весов или model card в проверенном дереве upstream не найдено. Инференс — Rust/tract-onnx 0.23.9, без Python.

Из каталога `companion` полный прогон запускается прежней командой с `PTT_LAB_A/B/C`, `PTT_LAB_OUT` и двумя необязательными путями: `PTT_LAB_DTLN_128` (по умолчанию `experiments/dtln-runtime/models`), `PTT_LAB_DTLN_512` (`experiments/dtln-runtime/models/512`). Пути по умолчанию считаются от каталога Cargo manifest; получение моделей — по README эксперимента. Отсутствующая или не загрузившаяся модель завершает тест ошибкой, строка не пропускается.

Импульс в полном прогоне проверяет задержки: none 0, raw Sonora 436 сэмплов (9,083 мс), FIR round-trip 126 (2,625 мс), обе DTLN 1662 (34,625 мс). Это внутренняя задержка обработки, без очередей устройства, готовности кадра, кодека и сети. Задержку из петли не вырезаем: она влияет и на возврат эха, и на обучение. Только опоры подбора и `aligned-clean.wav` сдвинуты для сравнения. DTLN работает на 16 кГц с FIR cutoff 7,2 кГц; её 4–8 кГц нужно читать рядом с контролем FIR + codec, отдельно от потерь самой сети.

У `EchoPath` импульс без эха проходит dry с задержкой 0: это не задержка engaged wet. Адаптер читает `gate_state()` после каждого 10-мс блока и сохраняет CSV (`capture_sample,engaged,score,lag_ms,last_transition_sample`). На стабильном dry опоры сдвинуты только на задержку кодека, на wet — ещё на 436 сэмплов. Из метрики исключается любое окно, чей полный STFT/fit support (4864 сэмпла, 101,33 мс) пересекает 10-мс crossfade, с дополнительным запасом 20 мс кодека с каждой стороны; граница crossfade перенесена на timeline декодера с учётом задержки кодека. Число исключённых и near-active окон печатается для каждого игрока. Холодные WAV и gate trace сохраняют переходы целиком. Контроли проверяют включение/выключение wet, исключение окон и задержку FIR; три исходных metric-теста и четыре речевых контроля сохранены.

CPU — process CPU time вокруг `far_end` + `near_end`, на игрока на обработанные 10 мс, включая FFT/FIR/очереди/детектор и адаптер. Загрузка моделей, кодек, симуляция комнаты, метрика и запись файлов исключены. Это среднее офлайн, не wall-clock latency вызова и не гарантия deadline устройства. Строки измеряются последовательно, без одновременной сборки/другого CPU-бенчмарка.

Intel i9-9900K, macOS 15.8, Rust 1.99.1, release: диапазон средних process CPU по игрокам, обоим сценариям и cold/warm в финальном прогоне. Строки, остановленные по вою, измерены только до остановки. Первый и финальный полные прогоны заняли 260/272 с wall time вместе с загрузкой, симуляцией, анализом и файлами; это не время одного обработчика.

| raw Sonora | 0,0905–0,1815 |

Все WAV теперь float32 mono 48 кГц, без нормализации или клиппинга при записи (входные голоса по-прежнему приведены к −24 dBFS, физический микрофон и микшер ограничены как раньше). Имя `{scenario}-{row}-{cold|warm}-{A|B|C}-decoded.wav` — декодированный передаваемый поток, `clean.wav` — исходная речь на capture timeline, `aligned-clean.wav` — опора на timeline декодера, `hears.wav` — динамик, `mic.wav` — речь + эхо до ограничения микрофона. Для сценария a сохранены пары `double-{decoded|aligned-clean}.wav` (23–30 с) и `triple-…` (34–41 с), для b `double-…` (16–27 с); в тёплом прогоне к отрезкам добавлены 10 с прогрева. При остановке по вою WAV обрезаются до полностью обработанных кадров, а недоступные отрезки получают `*-invalid.txt` с причиной и доступной длиной, без WAV с нулевым «результатом». Отдельные `control-{codec-only|resample-codec}-{A|B|C}-…` дают пол кодека и FIR на чистой речи вне замкнутой петли.

**Результат на исходных трёх голосах (24.10.2026).** В сценарии a `aec3-gate` остался dry у всех игроков до воя: 4,0 с холодного прогона и 3,5 с начала прогрева, как none/FIR. Поэтому строки double/triple talk для него отсутствуют; это не нулевая потеря речи. В сценарии b тот же адаптер действительно включает wet только у C: на 4,99 с холодного прогона и на 0,89 с прогрева тёплого. A/B остаются dry, и их потери совпадают с none. Исключены 1/355 окон у C cold (0,28 %) и 2/466 warm (0,43 %), у A/B 0; near-active исключений нет, C молчит. В сценарии a метрика целиком пропущена из-за воя; переключений и wet-блоков до остановки нет. Это поведение конкретной комнаты и голосов, не установленная причина: CSV показывает score, но не внутренний peak ratio, который тоже разрешает включение. Порог, production код и fixture не менялись ради результата.

- **Сценарий b.** Как и прежде, wet включается только у C, теперь на 1,69 с холодного прогона. A и B остаются dry.

## Сигнализация P2P через игру

Свой транспорт голоса договаривается через мод: `0x06 SIGNAL` компаньон → игра и `0x13 SIGNAL` игра → компаньон. Ниже то, на что этот канал может опереться, по локальным UDP-замерам от 2026-10-24 и справке `LuaHelpers` для 2.1.23. Условия измерений приведены непосредственно перед результатами.

**Путь.**
- Пакет компаньона попадает в Lua-UDP его копии игры, становится input action и вызывает `on_udp_packet_received` на каждом пире. `player_index` в событии — индекс отправителя, то есть игра сама подписывает отправителя.
- Мод отдаёт тело адресату через `send_udp(port, data, target)`. Отправка срабатывает только в копии игры адресата, поэтому копий на машину не больше одной.
- Хаб рядом с сервером говорит с игрой как игрок 0:
  - его пакеты в Lua-UDP порт сервера приходят с `player_index = 0`;
  - мод шлёт ему через `send_udp(hub_port, data, 0)`, и такой пакет уходит только с сервера.

  Так уже работает `radio.py` в контейнере стенда.

**Измерено пробой.** Условия замера: одна машина (Mac с сервером в VM), реальной сети между ними нет. Значения в одну сторону включают расхождение часов Mac и VM. Поэтому ниже результат этих прогонов, а не задержка или надёжность типичного сервера.
- Задержка:
  - только сервер — RTT p50 22–27 мс;
  - клиент → сервер → все — p50 93 мс к себе, 78 мс в одну сторону до сервера;
  - сервер → клиент — p50 68 мс в одну сторону.
- В прогоне 500 пакетов/с по 120 Б потерь не было.
- Двоичные тела, включая `\0`, прошли в обе стороны без искажений.
- В этих прогонах порядок на каждом пире сохранялся, пакеты приходили пачками по тику.
- Размеры от 16 Б до 65000 Б прошли, но первый пакет каждого нового размера от 4 КБ терялся, пока ОС растила буфер сокета.
- Во время автосохранения в замеренных прогонах пакеты не терялись: они копились и приходили пачкой с пиком задержки около 0,5 с. Справка ниже говорит, что при переполнении буфера потеря возможна, так что это не гарантия.

**Из справки 2.1.23.**
- Сокет запрашивает 256 КБ приёмного буфера. Всё, что сверх этого придёт между двумя вызовами `recv_udp`, теряется. Это относится и к паузе, и к сохранению: тиков нет, и `recv_udp` не вызывается.
- Каждый принятый пакет проходит через сервер мультиплеера ко всем клиентам. Поэтому входящий трафик надо держать как можно меньше: любое сообщение сигнализации видит каждый пир, даже если оно адресовано одному.

**Что из этого берёт мод и протокол сигнализации.**
- **Размер.** Тело `SIGNAL` (полезная нагрузка, которую мод пересылает, не разбирая) — не больше 1200 Б. Целый кадр — тело плюс заголовок кадра `0x06`/`0x13` с адресатом — остаётся ниже порога потери первого пакета в 4 КБ и в 200 с лишним раз меньше буфера. Мод отбрасывает кадр с более длинным телом, не пересылая. Точный размер `ANNOUNCE` здесь не считается: он зависит от кодека сигнализации, в котором кроме ключа и кандидатов есть ufrag, пароль и поколение рестарта ICE. Укладываться в 1200 Б, а если нет — делиться или отбрасывать кандидатов, обязан проверенный кодек сигнализации.
- **Повторы и порядок.**
  - Каждое сообщение идемпотентно и повторяется по таймауту: 1 с, затем удвоение до 8 с. Пауза, сохранение или переполнение буфера во время них задерживают или теряют сообщение.
  - Порядок сообщений одного отправителя сохранялся в замеренных прогонах, но протокол на него не опирается: устаревшую попытку отличает `attempt`, а не порядок прихода.
- **Время установки.** Не измерено. Оценка: KK — два сообщения через игру, подтверждение ключа идёт уже по UDP, то есть до первого прямого пути проходит два перелёта через игру плюс время ICE. Сколько длится перелёт на реальном сервере, проба не показывает. Всё это время голос идёт через игру.
- **Кому пересылать.** Сигнализация видна всем пирам, поэтому мод пересылает её только адресату, а `RTT` компаньон шлёт не чаще раза в 5 с. Допустимый адресат управляющего сообщения шире, чем голосовые множества POLICY:
  - любой игрок из текущего состава;
  - зарегистрированный хаб (игрок 0).

  Текущий POLICY задаёт права слышать и слать голос. Хаб или игрок другой силы, который служит только зашифрованным ретранслятором, слушателем быть не обязан, но `ANNOUNCE`, `RELAY_GRANT` и `BIND` до него доходить должны. Мод тело не разбирает. Принимающий компаньон сам проверяет сессию и грант, а медиа по любому пути принимает, только если её исходный отправитель и ревизия разрешены установленным POLICY. Право ретранслировать не даёт права слышать голос.
- **Пауза и сохранение.**
  - Установленные UDP-пути от тиков не зависят; физический микрофон всё же закрывается через 60 с без принятого POLICY (см. «Передача»).
  - Стоят сигнализация, запасной голос через игру и повтор START для плашки. Плашка застывает вместе с игрой: её таймауты тоже считают тики.

**Не измерено** (одна лицензия, второго клиента нет):
- два настоящих клиента через реальную сеть;
- пауза при подключённом клиенте;
- вход игрока во время сигнализации.

При входе мод обновляет ROSTER и POLICY, а HELLO нового компаньона включает его в медиамножества при наличии `pol1`. Компаньоны обмениваются `ANNOUNCE` через игру. Lua-тесты и процессные тесты переходов ниже покрывают обработчики и модели путей; вход двух настоящих клиентов через реальную сеть всё ещё требует живой проверки.

## Нагрузка и задержка

Оценка игровой копии при среднем Opus 40 Б и кадре 20 мс: 40 Б + 23 Б заголовка policy-медиа, 50 кадров/с — 3150 Б/с на говорящего до накладных расходов UDP и input action. Исходящий канал сервера для этой копии растёт как `N клиентов × S говорящих`; при 10 клиентах и 3 говорящих это ~94,5 КБ/с до накладных расходов. Клиенты без компаньона получают те же input actions. UDP-копии добавляют отдельный трафик по выбранным маршрутам; общий размер зашифрованного policy-медиа — Opus + 39 Б напрямую или +44 Б через relay, без IP/UDP. Исторический пробник выдержал 500 пакетов/с по 120 Б с одного клиента без потерь (RTT p50 134 мс); это не замер стоимости нынешней схемы на UPS.

Задержка «рот–ухо» на одной машине измерена сквозным стендом (см. выше): 152–153 мс после сброса запаса (было 240–262), из них ~85 мс транспорт игры. В реальной сети прибавляется пинг до сервера у обоих игроков, а настоящие устройства добавляют свою задержку ввода-вывода.

## Ограничения

- Пауза игры и автосохранение останавливают игровой путь и сигнализацию: тиков и `recv_udp` нет. Пакеты копятся в ограниченном буфере 256 КБ, затем возможны потери; после паузы компаньон сбрасывает лишний запас. Уже установленные UDP-пути работают независимо от тиков, но физический микрофон требует принятого POLICY раз в 60 с и затем закрывается. Гранты, новые пары и смена ключей зависят от игровой сигнализации. Долгая пауза с физическими устройствами и двумя настоящими клиентами не проверена измерениями ниже.
- Каждому игроку нужен флаг `--enable-lua-udp <порт>` в параметрах запуска Factorio; компаньон игру сам не запускает.
- Мод можно выложить на портал. Исполняемые файлы портал, по словам авторов модов, не принимает, поэтому компаньон распространяется через GitHub Releases.
- Любой локальный процесс может писать в Lua UDP-сокет игрока. Это допустимо: он может говорить только от имени этого же игрока.
- Копию отправленного голоса через игру получают все клиенты, независимо от `ptt-radio-scope`: каналы ограничивают воспроизведение у честных клиентов, но не экономят трафик игры и не обеспечивают конфиденциальность. По UDP-маршрутам голос уходит только слушателям из `send_to` текущего POLICY; после его установки AUDIENCE не может вернуть старые права.

Мод с каналами и POLICY, PTT и открытый микрофон, P2P/relay, `force`-область, упаковка и workflows выпуска уже реализованы. CI собирает компаньон для Linux, macOS и Windows; наличие сборки не заменяет проверку клавиши и аудиоустройств на каждой ОС.

## P2P transport contracts (v2, 2026-10-24)

`companion/src/transport.rs` and its `wire` and `signaling` modules define the types, pure codecs and interfaces of the P2P transport. The companion runtime (`companion/src/runtime.rs`) drives them: ICE connectivity (`connectivity/`), Noise pair sessions (`crypto/`), hub and player-relay registration (`transport/hub.rs`, `transport/relay.rs`) and per-pair route selection. The legacy v1 framing in `packet.rs` remains for HELLO, control messages, the transmitter's internal records and legacy receive compatibility. The active mod requires policy media; the v2 compatibility bridge remains in the test emulator. The codecs themselves do not authenticate or authorize decoded data; the session and relay layers above them do.

### Media identity and ordering

A logical frame is `(player_index u16, stream_generation u64, extended_sequence u32)`. The companion chooses a fresh unpredictable generation at startup and announces it through the trusted game channel. Only a current `ANNOUNCE` selects a stream generation; a delayed game frame naming another generation is dropped. A key change or path change preserves media identity, the decoder and the ordering queue. A restarted companion replaces the selected generation and clears the former stream. ANNOUNCE hashes bind the exact canonical encoded bytes of both selected announcement snapshots, including initial credentials and candidates, to the Noise session. Trickle updates do not mutate that snapshot or its hash. A credential restart selects a new ANNOUNCE snapshot and establishes a newly bound key session without changing media identity; established keys retain their original snapshot through overlap.

Sequence is u16 on both wires. Initialise the first reference to `0x10000 | u32::from(first_sequence)` so a reordered predecessor of an initial seq=0 can expand to 65535. `extend_sequence` chooses the nearest value to the accepted high water mark; older reordered frames do not move that mark backwards. Exactly half the u16 range is ambiguous and rejected. u32 underflow/exhaustion is explicit failure rather than wrapping into a duplicate identity; exhaustion requires a newly announced stream generation. The active ordering window must stay below 32768 frames.

`talkspurt u16` starts at 1 and increments once per PTT press, wrapping through 0. `serial_order` defines newer/older/equal and rejects the ambiguous half-range. Repeated START for the same talkspurt is idempotent; STOP closes only its own talkspurt. Older START/STOP/VOICE cannot reopen a closed talkspurt. VOICE for a newer talkspurt opens it when START was lost. A repeated game START every 250 ms keeps the badge alive without resetting or rebuffering the decoder. Retained talkspurt state must expire before half-range ordering could become ambiguous.

`PreDecodeOrder` is one queue per selected stream, shared by game and every UDP path. Its receiver is the sole owner and caller, immediately before `Mixer::voice(sender, seq, opus, now)` and the existing PCM queue. It deduplicates media identities before decoding, waits for a missing predecessor until `deadline()`, emits `Ordered::Missing` once, and drops that frame if it arrives after the cursor advances. `Missing.next` exposes the following compressed packet for the receiver's existing decoder to choose FEC or PLC; using it for FEC does not consume its later normal decode. `ReorderConfig.wait` starts at the measured secondary-minus-primary path delay plus 10 ms, and `max_frames` bounds storage. The receiver's implementation is `src/reorder.rs`, owned by the mixer (see «Приём»).

### UDP and relay wire

Integers are big-endian. The whole UDP datagram, including a relay wrapper, is at most 1200 bytes. Unknown types/kinds, reserved flags, malformed lengths and invalid fields produce a codec error; network callers silently drop them. A decoded UDP header is untrusted. The receiver first selects candidate keys by its locally allocated handle and phase, verifies the tag, checks the inner kind against the outer type, then applies replay, audience, current-generation and media-ordering checks. Replay state moves only after tag verification.

| Packet | Fields in wire order |
| --- | --- |
| Encrypted UDP | `type u8, flags u8, receiver_handle u32, counter u32, ciphertext, tag[16]` |
| Decrypted inner | `kind u8, sequence u16, talkspurt u16, body` |
| Relay wrapper | `0x10, grant_session u32, complete encrypted UDP datagram` |
| BIND | `0x11, stage u8, registration fields` |
| BIND_ACK | `0x12, challenge fields, proof[32]` |

Legacy encrypted type and inner kind values are VOICE=4, START=5, STOP=6, PING=7, PONG=8; active policy media uses types 9–11 and a revision prefix, as specified in [Companion policy transitions](#companion-policy-transitions). They are disjoint from STUN's first-byte range 0–3 ([RFC 7983, section 3](https://www.rfc-editor.org/rfc/rfc7983.html#section-3)). Only flag bit 0 (key phase) is defined. VOICE body is nonempty Opus; START/STOP body is empty; PING/PONG body is an eight-byte probe token. Probe sequence/talkspurt are correlation fields and do not enter media ordering. `ReceiverHandle` is a local key-slot handle advertised in NOISE1/NOISE2, distinct from player indices and relay session numbers. It selects the pair's current/pending/overlap keys, not a global per-player key. A handle is not reassigned while packets or keys from its prior session can still be accepted.

Player indices and both u64 stream generations are implicit in the authenticated pair context, not sent in every UDP media packet. `SessionContext` records these identities, the combined ANNOUNCE hash and key epoch. The Noise prologue binds protocol version, both players and stream generations in player-index order, both selected ANNOUNCE hashes, and the negotiated suite name. A raw header cannot supply or replace this context. The u64 nonce is `key_epoch u32 || counter u32`; counter is monotonic per key/direction across all routes and packet kinds. Counter exhaustion requires rekey before another packet. Each key/direction owns a 128-packet replay window. Old keys keep their existing window for five seconds; key phase cannot be reused while that overlap remains live.

The ANNOUNCE snapshot bytes are `signaling::encode(Signal::Announce(...))`, excluding the game envelope. The Noise pair-session section below pins their hash, combination, prologue and epoch allocation. Arbitrary public `SessionContext` values do not themselves prove authentication.

Media overhead is `10 outer + 5 inner + 16 tag = 31` bytes, or 36 through a relay. IP and UDP headers are excluded. The common Opus cap is 1164 bytes, so an unchanged encrypted datagram of 1195 bytes can be copied onto both direct and relayed routes. The direct outer codec can structurally parse up to 1200 bytes, but a datagram above 1195 cannot be relayed; the media codec uses the smaller shared cap. All routes carry the same encrypted bytes and nonce; the plaintext game copy is separately framed with the same media identity.

BIND stage 0 is `grant_session u32, hub_generation u64, player u16, attempt u64, client_nonce[32]`. One grant covers both endpoint slots; the relay verifies `player` equals its sender or recipient, verifies session/hub generation against the grant, and updates only that player's slot. Stage 1 adds the relay-observed endpoint, `challenge[32], expires_at_ms u64`; stage 2 adds `proof[32]` to that complete challenge. ACK repeats the challenge and has its own proof. Endpoints encode family 4/6, address[4/16], port u16, and for IPv6 flowinfo u32 and scope_id u32. Relay→destination forwarding retains the `0x10,session` wrapper around the unchanged encrypted datagram. The receiver can identify a relay route/session from it, but cannot treat it as authenticated speaker identity.

`bind_mac_input` pins the input order: the ASCII label `ptt-radio-v2 bind commit` followed by one zero byte (or `ptt-radio-v2 bind ack` followed by one zero byte), then the grant's public fields `session u32, relay u16, sender u16, recipient u16, hub_generation u64, expires_at_ms u64`, then the complete stage-1 challenge in the order above. The registering player is therefore covered along with endpoint, attempt and freshness. The 16-byte grant secret is the HMAC key and is excluded from the input. Signaling `encode_grant` appends that secret after the same public fields. The relay requires an outstanding, unexpired, single-use challenge at exactly that source endpoint before changing a destination. Grant/session numbers and a captured proof alone do not authorize off-game network attackers to register. A rebinding needs a new challenge. Challenge generation, HMAC verification, role/grant checks, expiry checks, byte/rate limits and grant closure live in `transport/relay.rs` (see the relay section below).

### Game media compatibility

The outer game magic/version remain `R,1`. New kinds are START2=0x07, VOICE2=0x08 and STOP2=0x09. Companion-to-game fields are `R,1,kind,sequence u16,stream_generation u64,talkspurt u16,opus`; game-to-companion inserts the authoritative event player index u16 immediately after kind. Headers are therefore 15 and 17 bytes. Only VOICE2 carries Opus. The mod supplies the player identity, and the receiving companion checks the generation against its selected ANNOUNCE. This game path is plaintext and trusted to the game/server; UDP encryption does not make the game copy E2E encrypted.

The v2 codec accepts START2/STOP2 at exactly 15 outbound bytes and VOICE2 with 1–1164 Opus bytes after that header. These are compatibility formats. The active mod accepts only START3/VOICE3/STOP3 from a registered companion advertising `pol1`; it does not convert them for legacy listeners. The policy formats and revision admission rules are specified in [Companion policy transitions](#companion-policy-transitions).

The emulator in `companion/src/relay.rs` retains the earlier v2 bridge for pre-policy scenarios. It forwards v2 unchanged to listeners advertising `v2`, converts v2 to legacy kinds for other listeners, and keeps legacy synthetic STOP behavior. This is not the active mod's media policy. Current HELLO is `ptt-radio-companion <version> hud1 pol1 v2`; exact whitespace tokens are independent, and the five-byte hub registration declares none of them.

The mod stores each generation as eight opaque bytes, avoiding Lua number precision loss. Its policy-media talkspurt comparison uses the u16 half-range rule, including 65535 → 0 wrap; repeated START is idempotent, and stale START/STOP cannot replace a newer talkspurt. START3 or VOICE3 may select a new generation, while STOP3 cannot. Each sender retains up to 16 retired generations; further generation changes fail closed without evicting old identities. This history expires after 60 seconds without accepted policy media, or on departure/15-second companion timeout. HELLO heartbeats preserve active and retired identities. Badge expiry hides the badge without a synthetic media STOP: UDP audio may still arrive, and receiver PCM cleanup is independent. Repeated START refreshes the badge without restarting the talkspurt. The receiving companion still checks the generation selected by trusted ANNOUNCE.

### Signaling schema and trust

Game SIGNAL is kind 0x06 outbound (`peer u16` is destination) and 0x13 inbound (`peer u16` is the game-derived sender). The body starts with schema byte 2 and message kind u8. The game signaling bridge limit is 1200 opaque body bytes, plus the five-byte game envelope; the Rust codecs conservatively cap the whole encoded envelope at 1200 bytes. The mod does not parse the body. It routes to any connected roster player, target 0 for the registered hub, or target 0xffff for the roster and registered hub, independently of voice scope. Input with outer kind 0x13/0x14 is ignored, and a nested AUDIENCE stays inside the opaque 0x13 envelope. The codecs validate framing and bounds, not candidate syntax or authorization. Each game peer observes every SIGNAL input action, including ICE credentials and RELAY_GRANT secrets. The agreed trusted-game model trusts connected players with those values: BIND HMAC protects against off-game network attackers, not a hostile connected player able to claim an endpoint slot and black-hole encrypted traffic. The relay does not learn the voice session keys from a grant.

The headless hub registers only through engine-authored player 0: exact bytes `R,1,HELLO,port u16be`, where port 0 selects 34555 and other ports must be at least 1024. HELLO repeats every five seconds and registration expires after 15 seconds, checked on the existing one-second maintenance tick. Delivery uses `helpers.send_udp(port, data, 0)`, which is server-only; player 0 is never looked up as a LuaPlayer. The hub receives ROSTER on HELLO and membership updates, without player mic settings. Its registration is not media-capable, so the current mod sends it no POLICY. The hub ignores roster and audience/policy messages in any case.

The active mod builds POLICY from connected players, channel eligibility and registered `pol1` capability on membership, capability and policy changes. It refreshes the saved snapshot on unchanged HELLO. Server 0 is not a media source under the hub registration. The old AUDIENCE codec and pre-policy runtime branch remain for compatibility and the emulator; their wire schema is retained below. Once POLICY is installed it owns media permissions and AUDIENCE cannot replace it.

`mod/tests/control_test.lua` executes the real event handlers against a small Factorio API fake; `relay.rs` exercises pre-policy control/media compatibility over real local UDP; policy process tests install authoritative snapshots separately. The emulator retains its tick, latency, jitter and stall model and adds roster/force controls for scenarios. These checks do not establish real multiplayer join/pause behavior or live GUI/audio rendering; the local UDP live-measurement qualifications above still apply. The mod owns no ICE or media cryptography.

| Body kind | Remaining fields, in wire order |
| --- | --- |
| 1 ANNOUNCE | `version u16, capabilities u32, suite_count u8, suites[u8], stream_generation u64, static_key[32], ice_restart_generation u32, ufrag bytes, password bytes, candidate_block` |
| 2 NOISE1 / 3 NOISE2 | `attempt u32, session_generation u64, receive_handle u32, noise bytes` |
| 4 KEY_CONFIRMATION | `attempt u32, session_generation u64, token u64` |
| 5 RTT | `probe u64, path, rtt_us u32` |
| 6 RELAY_GRANT | `session u32, relay_player u16, sender u16, recipient u16, hub_generation u64, expires_at_ms u64, secret[16]` |
| 8 ICE_CANDIDATES | `stream_generation u64, ice_restart_generation u32, candidate_block` |
| 9 RELAY_CLOSE | `relay_player u16, session u32, hub_generation u64` |
| 10 REKEY_REQUEST | `session_generation u64` |
| 11 GAME_PROBE | `probe u64, reply u8` (0=request, 1=reply) |

`bytes` is `length u16 + bytes`, nonempty; strings must be UTF-8. Credentials are capped at 256 bytes each, Noise at 1024. `candidate_block` is `complete u8 (0/1), count u8, candidates[bytes]`, at most eight SDP candidate attributes of 512 bytes each and still within the whole-message cap. The ICE crate converts candidate SDP; this module does not duplicate its grammar. Additional candidates use trickle messages scoped to both the selected companion stream generation and its ICE restart generation; the ICE owner rejects mismatches on either field, including late records from a previous companion with the same restart number. Each restart exchanges fresh credentials and candidate records. Credentials must come from an OS CSPRNG, including at restart; callers must not rely on the tested `is` 0.11.1 convenience `IceCreds::new`, whose underlying generator is noncryptographic.

AUDIENCE has its own mod-authored game kind 0x14: `R,1,0x14,reserved_sender u16=0,revision u64,send_to player_set,receive_from player_set`. `Audience`, `encode_audience` and `decode_audience` are separate from `Signal`; raw SIGNAL body kind 7 is reserved and rejected. The pre-policy emulator emits 0x14 from its own state; the active mod emits POLICY 0x15 instead and does not forward either control kind from companion input. Opaque player SIGNAL forwarding retains outer kind 0x13 and cannot produce 0x14, even for hub player 0. A nested AUDIENCE or old kind-7 body in player SIGNAL is rejected by the codecs. The reserved zero field preserves the mod-header shape; authorship comes from the mod's game-only dispatch, not a special sender identity. Local UDP has the same trusted-local-process boundary as existing MIC_STATE/HALF_DUPLEX.

Suites are AES-256-GCM=1 and ChaChaPoly=2, with no duplicates and at most two entries. Both sides select AES only if both advertise it, otherwise a common ChaChaPoly; no common suite means no UDP session. The smaller player index initiates KK and controls ICE. Retransmission repeats the same bytes for the same attempt; a new attempt uses fresh ephemeral keys. Concurrent rekey follows the smaller player's attempt. NOISE messages advertise each endpoint's own receive handle. `session_generation` and `attempt` scope pending-key and confirmation state; mismatches cannot activate a key.

KEY_CONFIRMATION carries correlation metadata, not proof that a key works. After NOISE2 the initiator sends an encrypted PING with that token under the pending key, even without media; the responder authenticates it and sends a matching encrypted PONG under that key. Authentication activates the corresponding pending key. Lost PING or PONG is retried with a fresh packet counter and the same confirmation token until the bounded attempt expires; old-key replay state survives the overlap. `tests/crypto_sessions.rs` covers key-confirmation loss without media.

REKEY_REQUEST lets the higher-index sender ask the lower index to replace the named current session generation, including before its outbound counter is exhausted. Retries repeat the generation. The lower index starts the new KK attempt; duplicate requests for the generation already being replaced resend that attempt's bytes. Stale requests cannot replace a newer session, and the pair checks the game-derived sender. This request changes no media identity or UDP header; the mod forwards it opaquely like other SIGNAL bodies.

`path` is `0` game, `1` direct, `2 + session u32` hub, or `3 + relay_player u16 + session u32` player relay. RTT probes measure the complete route, including both legs through a relay. `player_set` is `count u16 + players[u16]`, at most 256 strictly ascending unique indices. AUDIENCE is an authoritative mod message, not an accepted arbitrary player's SIGNAL. In the pre-policy compatibility branch, UDP media requires AUDIENCE; after POLICY installation, its permissions and revision replace that branch. Control signaling may reach hub player 0 and relays outside the voice audience; media authorization does not restrict connectivity/key signaling to those sets. MIC_STATE, HALF_DUPLEX and ECHO_STATE remain game-only and have no UDP inner kinds.

`Transport` is the socket/game I/O seam; `Path` names the selected route. It sends already framed bytes and returns raw bytes plus path, length and receive time. The socket/connectivity owner below this seam retains actual source endpoints for ICE consent and NAT rebinding. It dispatches a datagram to ICE only when its first byte is 0–3, it has at least the 20-byte STUN header, bytes 4–7 contain the magic cookie `0x2112A442`, and the big-endian body length in bytes 2–3 is a multiple of four and equals the datagram length minus 20 ([RFC 8489, section 5](https://www.rfc-editor.org/rfc/rfc8489.html#section-5)). These framing checks do not replace ICE transaction, integrity or consent validation. Types 4–11/0x10–0x12 go to their protocol decoders; malformed or unknown datagrams are dropped, and each path's checks apply before returning accepted traffic. `Received` does not expose the source endpoint because it is not speaker identity. Transport does not encrypt per path, infer a sender from an endpoint, choose a generation, or feed a decoder directly. Runtime route selection, redundant delivery, replay checks and audience enforcement remain explicit owners above this seam.

### Listener HUD quality

The companion advertises `ptt-radio-companion <version> hud1 pol1 v2`. Its `HUD_STATUS`
packet has the v1 header `52 01 0A 00 00`, then body version 1, a one-byte count
up to 32, and 15 bytes per record: sender BE16, opaque stream generation[8],
talkspurt BE16, level, route and delay class. The largest packet is 487 bytes.
The mod obtains the reporter from the input event, not the header's zero field.

The mod recognizes exact whitespace-delimited HELLO capability tokens in any
order. `hud1` enables reports; `pol1` enables active policy media. `v2` remains a
compatibility token; unrelated future tokens do not disable recognized capabilities. Without `hud1`, bars remain unknown. The
decoder validates the complete size, body version, count and enum ranges before
applying any record. Each record must name an active talker visible to that
reporter and match its eight opaque generation bytes and current talkspurt.
An identity or eligibility mismatch drops that record, not its valid neighbors.

Only the reporter's own row bars repaint. Reports expire exactly 300 game ticks
after arrival, and STOP, generation/talkspurt replacement, lost-STOP timeout,
capability loss and companion disconnect clear the corresponding cached state.
The expiry loop scans link tables only at the next stored deadline. A level-0
report can still show its selected route and unknown delay in the tooltip; it
stays grey. Echo replaces the bars, including during reports and expiry.

`mix.rs` measures each sender's last two seconds of measured playout, excluding
idle time and weighted by audio samples rather than packet count. Missing
packets mark their decoded PLC/FEC samples as impaired; undecodable samples and playout underruns
also count. Jitter overflow and backlog cuts count their discarded audio once
when the next slice plays. A late copy of an already concealed packet or a
duplicate adds nothing: the packet-level missing/discard counters do not feed
the metric. This measures continuity, including recovered audio, rather than
Opus fidelity or network packet loss alone.

Level 3 means less than 1% impaired audio, level 2 means 1% through 5%, and level 1
means more than 5%. Level 0 covers fewer than 500 ms of measured playout and a
playout observation stale by 300 ms. The 500 ms minimum counts rendered slices;
discarded duration does not shortcut it. History survives same-generation
talkspurt changes, but resets on a new generation or after 30 seconds without
playout. Repeated START does not reset it. Only selected v2 talkspurts actually
heard at playout are reported. STOP suppresses the record immediately. If a
talkspurt idles out without STOP, its record becomes unknown so a previously
green result cannot persist through the mod's expiry interval. The telemetry
subject expires two seconds after its last playout observation, so a lost STOP
cannot cause indefinite unknown heartbeats. Audio resuming within 30 seconds
refreshes the retained estimate from its first played slice; after 30 seconds
it starts another warmup window.

The receiver sends changed records at most twice per second and refreshes
unchanged records after two seconds. Batches favor the oldest report, including
never-reported senders, so more than 32 active talkers rotate fairly. When the
number of due talkers exceeds the four-batch capacity of a two-second interval,
the per-talker heartbeat necessarily takes longer; the batch rate and size
limits still hold. Route is the runtime's selected pair path (game/direct/hub/
player relay), independent of continuity. It describes the local selected route,
not the arrival path of every redundant media copy. Delay class remains 0:
route RTT alone does not establish mouth-to-ear delay.

The bands are product thresholds, not a perceptual calibration from the live
network lab. Deterministic tests exercise clean, fair and poor induced playout loss
with both 10 ms and 20 ms packets,
the exact 1%/5% boundaries, bounded discard recovery, 400/500 ms warmup, five-second
history retention, 30-second/generation reset, stale expiry, duplicates,
late copies, talkspurt replacement, batching and the shared wire vector. No
Internet or real-time lab measurement is implied by those tests.

### Noise pair sessions

`companion/src/crypto/mod.rs` implements a pure pair-session state machine using Snow 0.10.0 `Noise_KK_25519_AESGCM_SHA256` or `Noise_KK_25519_ChaChaPoly_SHA256` and stateless transport encryption. Its production caller is the companion runtime (`companion/src/runtime.rs`), which owns one session per pair. Both selected ANNOUNCEs must advertise AES to select it; otherwise the pair selects common ChaChaPoly. The configured Snow resolver obtains generated static and ephemeral key material from the OS random source. Key-bearing types omit `Debug`; persistence belongs to runtime.

The snapshot hash is SHA-256 of ASCII `ptt-radio-v2 announce`, NUL and the canonical raw ANNOUNCE bytes. The combined `SessionContext.announce_hash` is SHA-256 of ASCII `ptt-radio-v2 pair`, NUL, lower player BE16, lower snapshot hash[32], higher player BE16, higher snapshot hash[32]. Initial credentials and candidates remain in that immutable snapshot; trickle does not change it.

The Noise prologue is ASCII `ptt-radio-v2 noise`, NUL, protocol version BE16, lower player BE16, lower stream generation BE64, higher player BE16, higher stream generation BE64, lower hash[32], higher hash[32], suite-name length BE16, complete Noise suite name, session generation BE64, attempt BE32. Each Noise message encrypts its endpoint's receive handle BE32; the receiver checks it against the signaling wrapper.

Every fresh lower-side attempt increases the full u64 `session_generation`. Its separate checked nonzero u32 `attempt` becomes the key epoch, without truncating the generation. New attempts use fresh ephemeral material. Allocation skips the active key's parity and cannot reuse a retained old phase. Attempt/generation exhaustion fails closed. The nonce is epoch BE32 followed by counter BE32 interpreted as u64. Each key/direction starts its counter at zero, shared across kinds and routes. `u32::MAX` is reserved; `needs_rekey()` becomes true at `u32::MAX - 1024` and exhausted encryption fails.

After NOISE2 the initiator sends confirmation metadata and pending-key PING with sequence/talkspurt zero. The token is the first eight SHA-256 bytes of ASCII `ptt-radio-v2 confirm`, NUL and the final Noise handshake hash, interpreted as BE64. Both ends derive it, so metadata loss or reordering cannot block confirmation. The responder activates on matching authenticated PING and returns PONG; the initiator activates on matching authenticated PONG. Retries use the same token with fresh counters. Noise retries repeat the same attempt bytes. Old keys retain their existing replay windows for five seconds after local activation. Tag, duplicated kind, inner bounds and pending-confirmation validation precede replay commit.

Runtime constructs one `Session` from selected trusted local/remote snapshots and the local private key. The lower player calls `begin` with a greater generation and globally reserved receive handle. `on_signal(sender, signal, new_handle, now)` checks the game-derived sender. `receive` takes unwrapped encrypted datagrams; source consent, relay validation and audience policy remain outside. Runtime sends returned actions and copies each encrypted datagram unchanged across redundant routes. Authenticated media then enters existing stream ordering; key changes preserve stream identity.

Either endpoint can call `request_rekey`. Lower starts or retries KK; higher retries `RekeyRequest` naming its active generation. Duplicates reuse the pending attempt; stale requests cannot replace newer state. A new handle is consumed only by a fresh lower attempt or fresh NOISE1 response. Callers reserve handles while pending, active or old keys remain live; allocation need not be monotonic.

Runtime retries a handshake every 500 ms through a fixed ten-second deadline, then calls `abort_pending`. Preconfirmation abort permits a fresh attempt after a one-second pause, retaining burned attempt/generation IDs. After confirmation, `ResetRequired` drops UDP selection and publishes a fresh local ANNOUNCE/ICE snapshot. The receiver refreshes its snapshot in response; the initiating endpoint waits for that replacement before constructing another Session. The stream generation and media identity stay unchanged. `PhaseInUse` retains the rekey request and retries it every 500 ms until the old five-second key overlap expires. An authenticated, inner-valid, replay-accepted packet of any kind can activate the pending key: all PONGs lost alone need not force reset if a valid reverse PING or media packet proves the key. The total return-path failure test covers the bounded reset case.

`receive` returns an encrypted PONG action for each authenticated PING. Runtime sends it on the received full route, including relay wrapping when applicable, and must not also emit a second PONG through the connectivity probe scheduler. Authenticated PONG reception feeds that scheduler's outstanding-token check.

### Connectivity and route probes

`connectivity::PairConnectivity` owns one full `is = 0.11.1` ICE agent per selected peer pair, with the lower player controlling. Runtime supplies bound local socket addresses, sends each `DatagramTx` from its exact source, feeds source/destination tuples into `receive`, drains `poll_action`, and drives `handle_timeout` at `deadline`. Host/server-reflexive candidates support IPv4 and IPv6; the crate owns peer-reflexive discovery, authenticated checks, nomination and consent. Only the latest nominated `DirectRoute` is usable. This does not provide arbitrary non-nominated-pair sending or minimum-RTT ICE nomination.

The trusted ANNOUNCE owner selects the remote `StreamId`, then explicitly calls `select_remote` when that stream changes. Signals cannot select it implicitly. Newer ICE restart generations rebuild the checklist; lower generations and same-generation credential/initial-candidate mutations are rejected. A remote-only restart preserves local credentials. Local `restart` obtains OS-random credentials, increments the restart generation without wrapping, invalidates direct measurements and regathers mappings.

A player who leaves the game never gets the ROSTER that removes them, so after rejoining they may still hold a peer's old snapshot while that peer has rebuilt the pair. The runtime therefore keeps one floor, one above the highest restart generation any removed pair announced, and a rebuilt pair starts there (`PairConnectivity::start_at_restart_generation`); the holder sees an ordinary restart. Until a handshake message verifies against the current snapshots, a newer remote snapshot is taken as the answer to our own announce and does not restart ours, so the two sides cannot keep restarting in answer to each other (`Peer::unconfirmed`, test `review_regression_pair_recreated_after_roster_removal_reconverges_on_udp`).

On `PublishDescription`, build and cache the complete ANNOUNCE from `local_credentials()`, `initial_candidates()` and `initial_gathering_complete()`. Retry identical snapshot bytes, including keys and suites. Discovery publishes growing candidates separately through `PublishCandidates` and `candidate_signals()`, scoped to stream and restart generations. Send every returned chunk; each is bounded by the existing game-envelope codec, and only the final chunk carries completion. Publication retries use intervals of one, two, four and then eight seconds while no direct route is nominated; fresh discovery/checklist state resets that backoff. Runtime binds each newly selected snapshot to its crypto session. Full-snapshot validation beyond ICE fields remains with that owner.

The first-byte/cookie/length STUN checks precede parsing. `UntrustedApplication` admits only the current nominated tuple while ICE is connected. This is endpoint consent; runtime must still check the cryptographic tag, session, audience and media identity.

Reflection defaults to an 800 ms deadline, capped at two seconds, with at most four configured numeric STUN endpoints and no built-in public server. Without a hub, requests for matching address families are emitted in parallel. Replies must match socket, server and OS-random 96-bit transaction. A small XOR-MAPPED-ADDRESS decoder handles unauthenticated public STUN replies because the pinned ICE parser requires MESSAGE-INTEGRITY even on binding-success replies. Reflections remain untrusted candidates until ICE succeeds.

With a configured hub, discovery first waits for its game-authenticated grant and BIND reflection. `DiscoveryAction::BeginHubBinding { source, hub, request }` delegates the existing exchange; `BindClient::from_request` preserves that exact transcript. After verifying the grant, source challenge, ACK HMAC and expiry, runtime calls `authenticated_hub_reflection(source, hub, full_bind_challenge, now)`. At the 800 ms discovery deadline, sockets that received no authenticated reflection start a separate public-STUN window; this includes an unserved address family. Successful sockets are excluded from fallback. A raw ACK passed to `receive` cannot authenticate reflection.

`ProbeScheduler` registers each permitted route with a local revision, invalidating tokens and measurements on replacement. Registration alone does not establish liveness. The active talking route sends PING every 250 ms and becomes unavailable after one second without a matching authenticated PONG. When a live idle/backup route becomes the talking active route, it probes immediately and starts a fresh one-second budget at that transition; identical activity updates do not extend the budget. An already-expired idle deadline gets no transition grace, and activity changes alone never make an unavailable route live. Returning to idle restores the deadline from the latest authenticated PONG (or registration before any PONG). Other routes probe every second and expire after three seconds; unavailable routes continue probing for recovery. These intervals also satisfy the 15-second NAT keepalive bound.

`SendPing`/`SendPong` are intents for the named complete route, including both relay legs. Runtime authenticates and frames UDP probes with the existing eight-byte big-endian token. It derives the current `RouteId` from the actual route before calling `authenticated_ping`/`authenticated_pong`. PING alone never refreshes liveness; PONG must match an unexpired outstanding token for that route. Replayed, stale and cross-route replies cannot update RTT. `NetworkRtt` is separate from own-echo latency; incoming `Signal::Rtt` is not local measurement proof.

### Companion runtime

`runtime::Runtime` drains the accepted connectivity, crypto and relay cores. `runtime_io::Network` sends from each exact bound socket, or carries those same datagrams through `LabPath` with its real public source. Game datagrams stay on the game socket and are never labelled as direct traffic. The receive pump accepts game packets only from the configured game IP; the game may use a separate sending socket. MIC_STATE, HALF_DUPLEX and ECHO_STATE remain game-only. Capture/playout, half-duplex decode and the actual played AEC reference retain their existing thread ownership.

The default network adapter binds the default-route IPv4/IPv6 interfaces available without transmitting a discovery packet. `--udp-bind ADDR` repeats for up to four explicit interface/port pairs; `--hub ADDR` configures the server relay; `--stun-server HOST:PORT` repeats for public reflectors. Numeric addresses need no DNS. With no explicit reflector, the companion resolves `stun.l.google.com:19302` after HELLO on one worker, bounded to four names and four results. The receive pump polls a channel without blocking. The two-second bound counts from the lookup start, which precedes audio startup; a result already received is delivered even when first polled after that point, and only a poll that finds nothing at or past the bound reports a timeout, after which a later result is ignored. The OS resolver call cannot be cancelled by this wrapper: the sole worker may remain blocked until process exit, and shutdown does not join it. Failure or timeout disables optional discovery while game startup/media continue. Late results enter discovery without replacing an outstanding hub exchange; a result that adds no new server, including an all-failed lookup, changes nothing. `--game-only` suppresses UDP discovery, checks and relay operation. `--netlab ADDR --netlab-bind ADDR` uses the actual lab socket; the lab supplies its own reflector with `--stun-server` when needed.

Each pair starts on game immediately and switches to its first locally validated UDP route immediately. Among live routes, an improvement of at least 10 ms full-route RTT must persist for three seconds; disappearance of the active route switches immediately. An intentional optimization to a faster game route does not trigger another initial UDP transition. Equal RTT prefers direct, then server relay, then player relay. A player offers a pair only while its direct legs to both endpoints are locally validated; endpoint probes measure the entire relayed route rather than accepting a remote RTT report as local proof. The second route is another validated UDP route when present, otherwise game. One encryption per pair/logical packet supplies identical ciphertext to both UDP routes.

The companion sends HELLO with `hud1 pol1 v2` before starting media threads. Before POLICY, synthetic tone/WAV sources retain START2/VOICE2/STOP2 compatibility; the physical microphone stays closed. The pre-channel emulator bridge can convert the copy for a legacy recipient, while the current mod drops that media. The pre-policy bridge/emulator owns the old self-monitor opt-in, which AUDIENCE intentionally omits: unversioned own game echo remains compatible in that branch, while remote media fails closed without AUDIENCE. After POLICY, only versioned media and its explicit self-monitor permission are accepted. Runtime sends one plaintext game copy per logical packet even with two UDP routes. START refreshes every 250 ms, retaining talkspurt and sequence; a continuing authorized talkspurt can cross adjacent policy revisions.

Only ANNOUNCE selects a remote mixer generation. Until that selection, trusted game media may occupy one pending generation per player, bounded to 20 total records for 200 ms and at most 256 players. Duplicate voice and repeated START records do not consume additional slots. Expiry permits another generation to claim the pending slot. Selection drops mismatching records and releases matching records once in serial talkspurt/sequence order, including across u16 wrap, with STOP after the voice at its sequence. Authenticated UDP media cannot enter this hold. The selected generation uses the normal shared ordering queue, so released and subsequently repeated media retain one logical identity. A generation change clears the former decoder, queue and pending records; the local identity is selected when game registration identifies this companion.

Releasing a full compressed hold can exceed the existing 200 ms PCM queue, especially for 20 ms Opus frames. Admission and deduplication do not promise that every admitted frame becomes audible: the normal PCM overflow (`dropped_late`) and backlog shedding policies still apply. Retired game generations are filtered before they can occupy the pending hold.

Before POLICY, each trusted ROSTER authorizes the next AUDIENCE snapshot to reset its revision. A lower revision without that one-shot authorization clears both media scope sets and latches them closed until another ROSTER and snapshot; an arbitrary later higher snapshot cannot reopen them. Equal revisions are accepted normally. ROSTER alone does not discard a healthy scope or change player identity. This is a recovery boundary, not a game epoch: a reordered snapshot immediately after ROSTER is indistinguishable from its new authoritative snapshot without a protocol epoch.

Before POLICY, compatibility media send/receive checks use AUDIENCE; without either snapshot, runtime sends or accepts no UDP media. After POLICY, its TX flag, sets and revision checks govern media. Trusted peer SIGNAL remains available outside voice scope. ANNOUNCE selects the mixer stream and freezes each crypto snapshot; same-restart mutation and retired stream contexts are refused. BIND grants must name their game-derived sender as relay, include this endpoint in the pair, match the selected relay generation and remain unexpired. BIND retries are 500 ms through a ten-second budget; a retry after the five-second challenge lifetime uses a greater attempt and fresh nonce. An unavailable bound relay route starts another bounded BIND attempt. Player relays renew live offers, reoffer expired/closed pairs under the existing caps, and withdraw/reoffer on endpoint generation changes.

An ICE restart's hub request is raised above its binding's attempt floor before sending, and discovery retains that exact revised transcript for ACK matching. Attempt exhaustion is an explicit error; it preserves the binding/peer and does not prevent ticking other peers. Each peer retains at most 16 bindings without a reserved hub slot. Anti-replay history refuses further remote stream changes after 32 retired generations and relay changes after 16; it does not evict old identities and silently re-admit them. These limits require a companion restart once exhausted.

Game RTT uses SIGNAL body kind 11. A known peer's request receives one same-token reply; a reply never produces a reply. Only a current Game route's outstanding local token can update its RTT and liveness. UDP PONGs come exclusively from `Session::receive` and return on the complete arrival route, including its relay wrapper. Current route revisions scope their token checks.

`tx`, `rx` and `pull` remain logical frame/slice records; redundant media never adds another logical row. A pre-ANNOUNCE arrival records `hold`; accepted voice records `rx` once when released. START/STOP counters count selected/admitted arrivals and omit held control records. Separate `route`, `route_tx`, `switch`, `generation`, `key`, `duplicate` and `drop` records describe transport decisions. `network_rtt` records the full-route probe RTT separately from own-voice echo latency. The selected secondary-minus-primary RTT divided by two, plus 10 ms, updates the existing reorder queue's gap budget without replacing its decoder or identities; the wait is capped at 200 ms.

### Companion policy transitions

POLICY is mod-authored game kind `0x15`: `R,1,0x15,0,0`, schema byte `1`, revision `u64` BE, flags `u8`, then the two AUDIENCE player sets. Flag bit 0 permits TX and bit 1 permits self-monitor; other bits and self-monitor without TX are invalid. Sets remain sorted, unique and bounded to 256 members. An empty send set is independent of TX permission. Off clears both flags and sets, including server 0. Once a valid POLICY is installed, AUDIENCE and unversioned ingress cannot reopen the legacy branch, including after an epoch reset.

UDP authenticated policy kinds are VOICE `0x09`, START `0x0a`, STOP `0x0b`. Their inner body begins with revision `u64` BE, followed by Opus only for VOICE. Outer and authenticated inner kinds must agree. Policy Opus is bounded to 1156 bytes, eight fewer than legacy media, so the complete relayed datagram still fits 1200 bytes. Relay envelopes recognize these kinds and forward ciphertext without decrypting it. Game policy kinds START3 `0x0b`, VOICE3 `0x0c`, STOP3 `0x0d` preserve the v2 sequence/generation/talkspurt layout and add revision immediately before Opus, or at the end of START/STOP. The game still inserts the authoritative sender index in the existing position.

The receiver keeps its current policy R and only a numerically adjacent previous policy R−1. Current packets need current receive permission. Previous packets need permission under both policies; self audio additionally needs TX and self-monitor under both. Future revisions are dropped without buffering or relabeling. An identical POLICY refresh does not rotate the window or restart capture; equal-revision mutation without a trusted ROSTER boundary and an untrusted rollback are rejected. Skipping R→R+2 retains no previous window and purges receive state because an unseen intermediate revision may have revoked the pair. The mod must therefore fan out every revision to every connected policy-capable companion, including unaffected players; producers must not coalesce intermediate revisions or publish only changed recipients.

Every held record, compressed frame, pending PCM fragment and queued PCM slice retains its original revision. Admission, held release and mixer pull check that provenance. Removed senders lose reorder, PCM and held state rather than receiving a draining STOP. Unaffected speakers retain their decoder, jitter and sequence histories. An expired compressed frame leaves a reorder tombstone: it cannot reappear as a missing packet reconstructed by FEC from a newer revision. PCM generated during gap decoding is checked again before pull. Copies on different transports keep the same stream/sequence identity and remain duplicates even across an adjacent policy update.

The sender stamps the next encoded packet with its installed revision; already encoded output keeps its old stamp. Capture encoding and application enqueue run under the runtime lock, and TX permission is checked on each send and repeated START. Muting clears capture pre-roll and queued local media, then closes transmission without sending another voice frame. The private output queue tags locally authored media at construction; muting does not cancel opaque third-party relay forwarding or signaling. Re-enabling held PTT/open mic opens a fresh talkspurt; a TX or self-monitor flag change also restarts it. An unrelated adjacent epoch preserves both a continuing talkspurt and idle PCM pre-roll, which is encoded only when transmission begins. A fresh trusted ROSTER permits one lower policy epoch or an equal revision with changed contents: before accepting that reset the runtime rotates its generation/key context, retires former remote generations, rebuilds associations and clears mixer selections and pending/playout state. An identical equal-revision refresh remains a no-op after ROSTER, including ordinary HELLO refreshes. Delayed media from the old association cannot select the reset stream. An admitted START carries its revision into the speaker and starts its normal 60 ms START_WAIT clock before the first VOICE arrives.

Rendering holds the runtime fence from mixer pull through device-queue append, in the same runtime→mixer→samples lock order used by admission. Recording and trace writes occur after that render fence. A slice pulled before revocation therefore cannot append after its purge. The software output ledger records each contributor's remaining sample endpoint and interpolation carry, not per-speaker output PCM. Device consumption advances these endpoints. Silent and fully muted contributions are absent, and consumed carry no longer marks the rest of another speaker's slice. Removing a non-contributing player preserves queued output and resampler carry; it does not impose an unrelated gap.

When a revoked speaker actually contributed to still-queued mixed output, that software queue is silenced in place: its samples become zero, its ledger entries keep their lengths and lose their contributor tags, and its resampler carry resets. The queue must keep its duration. The echo reference already received those samples at render time, so removing them would let playout refill ahead of the device timeline, and the canceller's lag would shift by the removed length. Before this was fixed, a 960-sample purge moved a 12 ms local path to −8 ms, and warm echo reduction fell to 3–7 dB. Silencing can also mute a short queued part of an unaffected voice mixed with it; that bounded cut is accepted instead of storing and remixing per-speaker output. Its decoder/reorder/jitter state remains ready, so subsequent frames need no new warmup. At 48 kHz the deterministic maximum-queue test measures **1439 samples silenced, length unchanged, 29.979167 ms**: less than 20 ms is queued before a 10 ms append. Interpolation adds at most one source sample of carry; endpoint/consumption tests also cover 44.1 and 96 kHz output.

### Relay hub

`companion/src/transport/relay.rs` is the one forwarding core, a sans-I/O `Relay` used by the hub and by a companion acting as player relay. It never decrypts: it forwards the received `0x10, session` datagram byte for byte, wrapper included, in both directions. Time is injected as unix milliseconds, the clock of grant and challenge expiry. Grant secrets, session numbers, challenges and client nonces come from the OS CSPRNG (`getrandom` 0.3.4). Proofs are HMAC-SHA-256 (`hmac` 0.12.1) keyed by the 16-byte grant secret over `bind_mac_input`, and the relay checks them with the constant-time `verify_slice`. Grant-bearing types have no `Debug`, and the hub logs counters only.

**Grants.** The relay issues them; there is no request message. `Relay::offer(sender, recipient, now)` allocates a fresh nonzero session and secret and returns `RELAY_GRANT` frames for both endpoints. One grant covers both endpoint slots. It carries the relay's own player index and its game-session generation, and it expires after `grant_ms` (hub default 30 min). `set_generation` drops every grant at once, and a BIND naming another generation is refused. Each player may be an endpoint of at most `grants_per_player` live grants (default 64), and the table holds at most 4096. `RELAY_CLOSE` from an endpoint closes its grant and is passed to the other endpoint. `withdraw` is the relay's own close, sent to both. A closed or expired grant forwards nothing.

**BIND.**
- Stage 0 must name a live grant of the current generation and one of its two players. Its `attempt` must be above that slot's last committed attempt.
- The relay answers with a challenge to the observed source. That challenge reflects the endpoint's public address (BIND reflection) and expires after 5 s, never after the grant.
- A slot holds at most four outstanding challenges, one per source address. A retransmitted request from the same source gets the same challenge back.
- A commit counts only if its challenge equals an outstanding one byte for byte, arrives from exactly that challenge's endpoint before expiry, and carries a valid proof. The challenge is then consumed, the slot's destination moves to that address, and an ack with its own proof goes back.
- A retransmitted commit of the current binding, from the bound address, is re-acked without any change.

So a replayed request or commit, a commit from another address, a spliced proof and an old attempt cannot redirect a slot. A rebinding (NAT change) needs a new attempt, and the old address keeps the slot until the new commit succeeds. `BindClient` is the endpoint side: it builds the request, answers our own challenge, and verifies the ack, which returns the reflected address. An endpoint reusing a grant across restarts must pick a larger attempt; the hub instead re-grants a restarted companion (below).

**Forwarding.** A wrapped datagram is forwarded only when its source is exactly the registered endpoint of one slot of that session and the other slot is bound. A guessed session number, an unregistered source and unwrapped media all produce nothing. Each player has a byte budget of `bytes_per_second` (default 64 KiB/s, one second of burst). It is charged for what it makes the relay send: forwarded datagrams it sent, plus the challenges and acks addressed to it, which bounds BIND amplification. Above the budget, datagrams are dropped. Decode errors are drops, and per-grant state is bounded by the caps above.

**Hub** (`transport/hub.rs`, binary `ptt-radio-hub`). It is player 0 on the server's Lua UDP port.
- Every 5 s it sends the 5-byte registration `R,1,HELLO,port u16` from its receive socket to the server's Lua UDP address. The mod then delivers hub-bound SIGNAL to that port with `send_udp(port, data, 0)`.
- On an `ANNOUNCE` with `CAP_UDP`, it grants every pair of the announcer with an already announced player that has no live grant, sender being the lower index. Earlier grants are resent to the announcer alone.
- An `ANNOUNCE` with a new stream generation means a restarted companion: its grants are withdrawn and the pairs are granted afresh.
- Once a second, a pair's newest grant is renewed in the last quarter of its life if both endpoints bound or forwarded in that quarter. The old grant keeps working until it expires.
- A renewal (`Relay::renew`) takes the place of the grant it replaces under `grants_per_player`, so a pair at the cap still renews, while a grant for any other pair stays capped; a pair holds at most its old grant and one replacement, and the table cap still applies. A refused renewal is counted in the hub's summary. The hub retains at most 4096 failed pairs, bound to both ANNOUNCE generations and the relay generation, and retries once per tick until a fixed deadline 30 s after the old grant's expiry. After expiry it issues a fresh grant under the normal caps, so recovery needs no new ANNOUNCE. Ordinary expiry preserves retry authorization; endpoint close of the refused grant, relay withdrawal (even after expiry), endpoint restart and relay generation reset revoke it. A fresh grant an `ANNOUNCE` issues for the pair drops its retry record, so an endpoint closing that fresh grant ends the pair until the next `ANNOUNCE`. The relay keeps only bounded weak revocation watches while the hub holds retry records, reserves their session IDs, and prunes them when the records are dropped. No retry record contains a grant secret. A table that stays full beyond the deadline requires a new ANNOUNCE for recovery.
- AUDIENCE, ROSTER and other kinds are ignored. Media audience is not a forwarding permission; only grants are.
- The hub generation is random per process start, so a restarted hub invalidates all earlier grants.

Flags: `--public` (UDP address companions bind and relay through, default `0.0.0.0:34560`), `--game` (the server's Lua UDP address, default `127.0.0.1:34556`), `--receive` (local address for mod deliveries, whose port goes in HELLO, default `127.0.0.1:34557`), `--grant-ttl-s` (1800), `--player-grants` (64) and `--player-rate` (bytes/s, 65536).

**Player relay.** A companion chosen as relay for a pair runs the same `Relay` with its own player index and its own stream generation, the one its ANNOUNCE selects, because `Runtime::grant` accepts a grant only under the relay player's current stream generation. It calls `issue` for a new pair the runtime assigns it, `renew` before a grant expires and `withdraw` when it stops, and feeds game SIGNAL to `on_signal`. On its one UDP socket `claims(source, data)` separates relay input (BIND requests and commits, and wrapped datagrams from an endpoint registered on one of its sessions) from its own endpoint traffic.

**Build and deployment.** `docker/hub.Dockerfile` builds static musl binaries for Linux amd64/arm64 with `--no-default-features`, using a dependency layer before copying production source. The runtime image is distroless static Debian 13, runs as UID/GID 65532 and exposes UDP 34560. `.github/workflows/hub.yml` builds the two binary targets in parallel with per-architecture BuildKit caches; its tag-only image job reuses those caches and publishes `ghcr.io/vshuraeff/ptt-radio-hub`. CI on `master` warms the same caches. These files define the build and publication path, not evidence that a public image has already been published.

The stand uses `stand/compose.hub.yaml`; live acceptance steps are in `stand/ACCEPTANCE.md`. `tests/relay_hub.rs` covers the forwarding core, hub policy and a NATed forward through the lab router core. The hub does not answer STUN, and its generation does not follow a game server restart while the hub keeps running.
